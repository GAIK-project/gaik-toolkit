## Executive Summary

The GAIK Solution Configuration Wizard is an agentic assistant that helps users design, validate, prototype, and package GenAI use cases using the GAIK toolkit. It translates a user's business problem into a structured specification, selects suitable GAIK software components or software modules, generates an executable JSON blueprint, creates a visual workflow for review, builds a minimal proof of concept, and then expands the proof of concept into a complete executable use-case package.

The wizard is intended for users who may understand their business problem but may not know which GenAI components, prompts, schemas, parsers, transcribers, RAG modules, validators, or evaluation tools are required. It acts as a bridge between business-level use-case thinking and technical implementation. The main output is a reusable package that contains code, prompts, schemas, workflow files, documentation, tests, and evaluation assets.

The wizard produces two complementary blueprints that serve different but equally important roles:

**The JSON blueprint** is the executable source of truth. It captures the complete technical configuration of the use case: input and output artifacts, selected GAIK components and their options, workflow steps, schemas, prompts, model settings, validation gates, evaluation plan, and deployment assumptions. It is the artifact that drives code generation, validation, PoC scaffolding, and documentation.

**The BPMN visual blueprint** is the business-process view. It is a standards-based BPMN 2.0 model — with swimlanes for each stakeholder role, typed tasks (user tasks, automated AI steps, human-review tasks), gateways, data objects, data stores, and message flows — that makes the solution legible to business analysts, domain experts, and decision-makers. It is generated from the JSON blueprint and linked to it element-by-element through stable identifiers (`visualizations.bpmn_mapping`), so every business-process element traces back to its technical counterpart. The BPMN is kept in sync by editing the JSON and regenerating; in V2 the BPMN canvas becomes directly editable with changes written back to the JSON.

The wizard is delivered in **two releases**:

**V1 -- Current Release**
Complete requirement collection (full business / technical / target-output specifications with a completeness gate), component-option awareness, PoC scaffolding with BPMN visual blueprint and documentation suite. Runs as a single-agent `SKILL.md` with no sub-agents.

**V2 -- Future Release**
All V1 capabilities, plus full use-case package generation, reference card auto-generation + Graphify integration for component intelligence, and a web-based hybrid editor with a live BPMN canvas.

| Capability | V1 (current) | V2 (future) |
|---|---|---|
| Conversational requirement collection (full Section 8 model) | ✓ | ✓ |
| Requirement completeness gate (Section 9 checklist) | ✓ | ✓ |
| Component selection and option-awareness | ✓ | ✓ |
| Executable JSON blueprint + validation | ✓ | ✓ |
| Mermaid workflow diagram | ✓ | ✓ |
| BPMN visual blueprint | ✓ | ✓ |
| PoC scaffolding (runnable Python package) | ✓ | ✓ |
| PoC validation and refinement (Gate 3) within the wizard's web interface | ✓ | ✓ |
| Documentation suite (5 docs generated from blueprint) | ✓ | ✓ |
| Full installable use-case package (Section 17) | — | ✓ |
| Reference card auto-generation + Graphify integration | — | ✓ |
| Interactive BPMN and JSON editing (canvas / panel / chat) | — | ✓ |

## 1. Purpose of the Wizard

The purpose of the Solution Configuration Wizard is to make GAIK use-case development more systematic, repeatable, and accessible. Instead of manually deciding which components to use and how to connect them, the user can describe the target use case in natural language. The wizard then guides the user through a structured process that results in an executable configuration and a working package.

The wizard supports three main goals:

1. **Use-case discovery and clarification**: help the user define what problem the solution should solve, who will use it, what inputs and outputs are involved, and what constraints must be respected.
2. **Solution configuration**: select the required GAIK software modules and lower-level building blocks, define prompts and schemas, and generate an executable JSON blueprint.
3. **Use-case implementation support**: create a proof of concept, validate the result with the user, and then generate a complete use-case package with code, tests, evaluation scripts, documentation, and workflow artifacts.

The wizard should not be treated as a simple code generator. It is a configuration and implementation assistant. Its value is in turning incomplete business descriptions into structured, validated, and reusable technical artifacts.

---

## 2. Scope

The wizard focuses on GenAI use cases that can be implemented using GAIK's existing software components or software modules. It supports at least the following use-case families:

- Audio or video to structured data
- Document to structured data
- Complex document parsing and extraction
- Vision-based extraction from images, scanned documents, charts, or technical drawings
- Retrieval-augmented generation over document collections
- Conversational access to internal knowledge
- Report, summary, or proposal generation
- Document classification
- Text-to-SQL or question answering over structured databases
- Validation and evaluation of generated or extracted outputs

The wizard also supports hybrid use cases -- for example, audio transcription followed by structured extraction and report generation, or document parsing followed by RAG-based question answering.

**Each scope entry names a pipeline pattern, not a single component.** "Audio or video to structured data" implies a sequence that may involve Transcriber, TranscriptEnhancer, SchemaGenerator, DataExtractor, and a validation step -- all wired together through typed intermediate artifacts. The wizard resolves these chains automatically: it first checks whether a single GAIK software module covers the needed workflow; if not, it composes a custom pipeline from individual software components. A user who describes an incident reporting system will get a 5-6 component pipeline, not a single black-box call.

## 3. Core Principles

### 3.1 Artifact-Driven Interaction

Every phase should produce an artifact that can be inspected, saved, edited, reused, or versioned. The conversation is only the interface. The durable outputs are specifications, blueprints, schemas, prompts, workflow files, code, tests, and documentation.

### 3.2 JSON as the Executable Source of Truth

The JSON blueprint is the executable configuration object. It drives code generation, validation, PoC scaffolding, and documentation. The BPMN visual blueprint is derived from it and provides the standards-based business-process view for stakeholder communication and review. Each plays a distinct role: the JSON stores what the system does; the BPMN communicates how the business process works. Separating the two avoids conflating technical implementation details with process-level communication, and keeps each artifact in the format most appropriate for its audience.

### 3.3 Human Validation Before Build

The wizard should not move directly from a short use-case description to code generation. It should first create a structured specification, ask the user to confirm it, generate a workflow blueprint, ask the user to validate it, and only then create the proof of concept or final package.

### 3.4 Agent-Driven Component Selection (Module-First)

Component selection uses the **same logic in every release (V1)**. The agent selects components by reading the registry fields directly -- `input_artifact_types`, `output_artifact_types`, `best_for`, and `known_limitations` -- and reasoning from them. There are no scoring tables, score boosts, or `selection_rules` files: those would have to be hand-maintained for every new component, whereas a registry entry already carries everything needed to choose.

Two deterministic rules constrain that reasoning:

1. **Module-first**: when a single GAIK software module already covers the needed workflow end-to-end (its input/output artifact types match the use case), the agent selects that module first. Lower-level building blocks are selected when the use case needs a custom pipeline, additional validation, special parsing, or non-standard orchestration.
2. **Validator as safety net**: every selection is checked by `BlueprintValidator` (component exists, artifact-type compatibility, required parameters present). A wrong selection is caught there, not by a scoring heuristic.

Adding a new component is therefore a one-file change: add its registry entry. What grows across releases is not the selection logic but the depth of **information retrieval** used once a component is selected (e.g., registry-as-index in V1-V1; reference cards + Graphify in V2 -- see Section 13.4).

### 3.5 Traceability

Every selected component should be linked to the requirement that caused it to be selected. This makes the generated solution easier to explain, debug, audit, and improve.

### 3.6 Skill as Orchestration Layer, Code as Implementation Layer

The Claude Skill (`SKILL.md`) is the user-facing interaction and orchestration layer. It manages conversation flow, asks follow-up questions, drafts specifications, explains tradeoffs, and calls implementation scripts. It is the pilot, not the aircraft.

All durable logic -- schema validation, component registry lookup, blueprint validation, Mermaid generation, PoC scaffolding, package structure -- lives in normal Python code outside the Skill instructions. This ensures that:

- Individual validators and scaffolders are unit-testable
- The wizard can be called from a CLI, CI pipeline, or future web UI without Claude
- Logic is versioned as code, not embedded in a prompt
- Each script can be developed and improved independently

The Skill orchestrates by calling scripts: `validate_blueprint.py`, `generate_mermaid.py`, `scaffold_poc.py`, `scaffold_package.py`. The scripts do the work; the Skill connects them.

### 3.7 Safe Defaults

The wizard should use conservative defaults, especially for privacy, human review, evaluation, data retention, and automatic submission to external systems. For example, any workflow that produces safety, legal, HR, financial, or operationally sensitive outputs should include a human review step by default.

### 3.8 Staged Agent Architecture

The wizard is experienced as one assistant but designed as a pipeline of specialized stages. Each stage receives the current blueprint JSON and returns an updated blueprint or a structured diff. This keeps any single stage from accumulating too much context, and allows each to be tested and replaced independently.

```
RequirementCollector
    -> SpecificationBuilder      (includes RequirementCompletenessChecker)
    -> SchemaDesigner            (conditionally: before or after ComponentSelector -- see Section 7.5)
    -> ComponentSelector
    -> ArtifactRegistry
    -> BlueprintBuilder
    -> BlueprintValidator        (must pass before visualization)
    -> WorkflowVisualizer        (Mermaid in V1+; BPMN in V1+)
    -> PoCScaffolder             (V1+)
    -> PackageBuilder            (V2)
```

**How the stages are realized changes by release, but the pipeline shape does not:**

- **V1-V1**: the stages are realized as a **single `SKILL.md` orchestrator** (one agent) that runs them as sequential phases, calling deterministic Python scripts (`validate_blueprint.py`, `generate_mermaid.py`, `generate_bpmn.py`, `scaffold_poc.py`, `check_requirements.py`, `generate_docs.py`). The whole flow -- including V1's complete requirement collection, component-option awareness, and documentation generation -- fits comfortably in one context window, so separate sub-agents would be pure overhead. Stages that are deterministic (ComponentSelector's module-first rule, ArtifactRegistry, BlueprintValidator, WorkflowVisualizer) live in code; the interpretive stages (RequirementCollector, SpecificationBuilder) are roles the single agent plays.
- **V2**: as package generation and interactive BPMN editing enlarge the state, stages may be split into **independent sub-agents** (e.g. via the Agent SDK), each receiving the blueprint JSON and returning a validated diff. The V1 structure already does the structural decomposition, so this migration is mechanical.

**StateRouter contract**: each stage receives the full `use_case.blueprint.json` and returns either a complete updated blueprint or a structured diff. The blueprint JSON is the shared state object -- not agent memory or conversational context.

**Proposal-validation loop**: within each phase, the LLM and the rules engine interact through an explicit cycle:

```
LLM proposes  ->  Rules validate  ->  User approves  ->  Blueprint updates
```

The LLM is responsible for interpretation, drafting, clarification, and explanation. The rules engine is responsible for registry lookups, type compatibility checks, artifact existence, required parameter presence, and acyclicity. The LLM may propose blueprint drafts or structured diffs, but no change is persisted until it passes validation and, where required, user approval.

> **Note on BPMN editing**: in V1 the BPMN visual blueprint is read-only — it is generated from the JSON blueprint and kept in sync by editing the JSON. Synchronized BPMN-JSON canvas editing, step configuration panels, and natural-language blueprint change requests are V2 features.

## 4. Key Concepts

### 4.1 Use Case

A use case is a business or operational task that the user wants to support with GenAI. A use case has a domain, users, inputs, outputs, workflow, constraints, expected value, and success criteria.

### 4.2 Business Specification

The business specification describes the use case in business terms. It includes the problem, current process, users, stakeholders, pain points, value proposition, target outputs, and success criteria.

### 4.3 Technical Specification

The technical specification describes implementation-relevant requirements. It includes input types, output formats, language, data sources, model preferences, security constraints, integration needs, runtime interface, validation needs, and evaluation methods.

### 4.4 Target Output Schema

The target output schema defines the structured artifact that the system should produce. For extraction use cases, this may be a Pydantic model or JSON Schema that defines fields, types, descriptions, required fields, confidence scores, and validation rules.

### 4.5 Software Module vs Software Component

The wizard distinguishes two levels of GAIK capability:

| Type | Definition | Selection rule |
|------|-----------|---------------|
| **Software module** | A complete workflow-level capability that packages multiple components into a single, reusable pipeline (e.g. `AudioToStructuredData`, `DocumentsToStructuredData`, `RAGWorkflow`) | Select first if it covers the use case end-to-end |
| **Software component** | A lower-level building block with a single well-defined responsibility (e.g. `Transcriber`, `TranscriptEnhancer`, `DataExtractor`, `LLMJudge`) | Select individually when no module fits, or when the user needs custom control over specific steps |

If one software module covers the use case, select it and use its pre-wired component sequence. If no single module applies, or if the user needs to omit, add, or reorder steps, compose a custom pipeline from individual software components.

**Example -- incident reporting from spoken observations:**

- Input: audio recording
- Output: structured incident report JSON
- Selected pipeline (no single module covers the full chain including validation):

  1. `Transcriber` -- speech to text
  2. `TranscriptEnhancer` -- ASR error repair
  3. `SchemaGenerator` -- build typed extraction schema
  4. `DataExtractor` -- fill schema fields from transcript
  5. `LLMJudge` -- hallucination and completeness validation
  6. Human review -- approve before submission

### 4.6 Schema Designer

The Schema Designer agent handles structured output definition for extraction and generation use cases. It takes field definitions collected by `SpecificationBuilder`, invokes the GAIK `SchemaGenerator` component, and produces `output_schema.py` (typed Pydantic model) and `requirements.json` (parsed field specifications). These files are referenced by `BlueprintBuilder` and by the runtime `DataExtractor` or `VisionExtractor`. By making schema design a named agent step, the wizard can explicitly ask the user to review and confirm the output schema before component selection proceeds.

### 4.7 Component Registry

The component registry is a machine-readable catalog of GAIK software modules and software components. Each entry describes input artifact types, output artifact types, capabilities, required and optional parameters, supported providers, quality tradeoffs, known limitations, and example blueprint steps.

### 4.8 Executable JSON Blueprint

The executable JSON blueprint is the main configuration artifact. It combines the business specification, technical specification, selected components, workflow steps, prompts, schemas, validation settings, evaluation plan, and build instructions.

### 4.9 Visual Workflow

The **BPMN visual blueprint** is the business-process view of the solution, generated from the JSON blueprint and linked to it element-by-element. It is a standards-based BPMN 2.0 model that shows the process in terms stakeholders understand: swimlanes for each role (users, reviewers, AI system, external parties), typed tasks, gateways, data objects, and message flows. Its purpose is stakeholder communication, process review, and governance — not runtime execution. In V1 it is read-only; in V2 it becomes directly editable with changes propagated back to the JSON blueprint.

### 4.10 Proof of Concept

The proof of concept is a minimal executable implementation that demonstrates the core workflow with uploaded or synthetic data. It should allow users to inspect outputs and adjust prompts, schemas, model parameters, and validation settings.

### 4.11 Final Use-Case Package

The final use-case package is a standard executable project folder containing all files needed to run, test, evaluate, and document the use case.

### 4.12 Blueprint Change Operation (V2)

A blueprint change operation is a structured record of a user-requested modification. It may add a workflow step, remove a task, change a component, update a model parameter, replace a prompt, change a schema, add a human-review gate, or alter an evaluation setting. Change operations are recorded in the blueprint change log so that design decisions remain auditable and reversible.

### 4.13 BPMN-JSON Element Mapping (V2)

The BPMN-JSON element mapping links each visual workflow element to its corresponding JSON object through a stable identifier. This mapping allows the wizard to open the correct technical configuration when the user clicks a visual task in V2.

## 5. Release Plan

### Release V1 -- Current Release

**Target**: Claude Skill deployable in Claude Desktop, Claude Code CLI, or via the Claude Agent SDK (web interface). Conversational, file-based, single `SKILL.md` agent — no sub-agents.

**Capabilities**:
- Full requirement collection dialogue using all fields defined in Section 8 (business-level, technical-level, target output requirements), collected in thematic rounds
- Three §8.1 fields (`use_case_name`, `domain`, `knowledge_processes`) captured in Phase 1; remaining fields collected in Phase 2 thematic rounds
- Requirement **completeness gate** (Section 9 checklist, 13 points) before component selection; the wizard asks follow-up questions for missing items instead of silently recording assumptions
- Pattern classification (audio-to-structured, document-to-structured, RAG, classification, hybrid)
- **Component-option awareness**: the wizard reasons about the behaviour-changing options each component/module class exposes and either infers them from the collected requirements or clarifies them with the user (e.g. Finnish audio → `Transcriber(enhanced_transcript=True)` instead of a separate `TranscriptEnhancer` step; `human_review=yes` → `VisionExtractor(include_verification=True)`)
- **Reference-card completeness**: every component/module in the registry has a reference card with structured `options` (behaviour-/selection-relevant options with `infer_from` hints). Card auto-generation and Graphify integration are V2.
- JSON blueprint generation with ArtifactRegistry enforcement
- BlueprintValidator: artifact existence, component compatibility, required parameters, acyclicity, terminal step, redundancy warnings
- **BPMN 2.0 visual blueprint** (`workflow.bpmn`): a standards-based business-process model with swimlanes for each stakeholder role, typed tasks (user tasks, automated AI steps, human-review tasks, send tasks), parallel and exclusive gateways, data objects, data stores, and message flows. Linked element-by-element to the JSON blueprint via `visualizations.bpmn_mapping`. In V1, changes to the process are made in the JSON blueprint and the BPMN is regenerated; in V2 the BPMN canvas becomes directly editable.
- Mermaid workflow diagram (`workflow.mmd`): a lightweight flowchart for quick technical validation during development.
- PoC scaffolding: minimal runnable Python package from the blueprint, with schema generation (one SchemaGenerator API call), extraction prompt, evaluation script, and sample-input support
- PoC validation and refinement (Gate 3): the wizard classifies feedback as intent changes (blueprint-first) or implementation fixes (PoC direct)
- **Documentation suite** generated immediately after PoC scaffolding (see Section 18): GenAI product canvas, technical specification, user guide, developer guide, evaluation plan. Documents are pre-filled from blueprint facts; narrative markers are filled by the agent.
- `governance.data_handling` is recorded as descriptive metadata in every blueprint

**Information retrieval model:**

The registry is the index; files are the content. Each agent reads only what it needs:

| Agent | Information source |
|-------|--------------------|
| `ComponentSelector` | Registry JSON fields (`input/output_artifact_types`, `best_for`, `known_limitations`) + reference-card `options` |
| `BlueprintBuilder` | Registry JSON + `example_blueprint_steps` + reference cards |
| `PoCScaffolder` | `readme_path` + `example_script_path` + reference cards |
| `PackageBuilder` | `readme_path` + `example_script_path` + reference cards |

Card auto-generation and Graphify queries are V2.

### Release V2 -- Future Release

**Target**: Full use-case package generation, reference-card auto-generation + Graphify integration, and a web application with embedded BPMN canvas and full synchronized BPMN-JSON editing.

**Capabilities** (all V1 capabilities, plus):
- **Full use-case package generation** (see Section 17): the standard installable Python package layout, configs, tests, and scripts
- **Reference card generation**: a script that derives one structured card per component from its source, README, and example (class name, import path, constructor params, main method signature, return type, minimal importable example -- see Section 13.4), plus **Graphify integration** (cards added as nodes in the knowledge graph, queried for both API contracts and relationships) and a graph-freshness check
- Hybrid blueprint editor with four connected areas:
  1. **BPMN canvas** -- visual process editing (bpmn-js or Camunda-compatible)
  2. **Step configuration panel** -- linked JSON technical settings per selected task
  3. **JSON preview** -- advanced inspection of full blueprint
  4. **Wizard chat** -- natural-language change requests
- Three editing channels:
  - *Visual BPMN editing*: process-level changes → translated to JSON change operations
  - *Step configuration panel*: technical changes → structured blueprint update validated before saving
  - *Natural-language chat*: interpreted → proposed change operation → user confirmation → JSON update
- Blueprint change operation format (structured, logged, reversible)
- `bpmn_mapping` section in blueprint linking each BPMN element to its JSON object by stable ID
- BlueprintValidator runs targeted re-validation on affected steps after each change; BPMN regenerated from updated JSON after each approved change

**Synchronization cycle**: generate BPMN from JSON → user edits via canvas / panel / chat → convert to JSON change operation → validate updated JSON → regenerate BPMN → user approves

**Graphify use in V2**: the unified Graphify graph (with embedded reference card nodes) is used heavily throughout V2 for interactive editing support:
- When the user clicks a BPMN task, the step configuration panel queries the graph for the component's card to populate constructor params, supported providers, and quality tradeoffs
- When the user requests a change in natural language (e.g. "use a cheaper model for this step"), the wizard queries the graph to identify compatible alternatives
- Impact analysis: when a step is modified, the graph identifies all downstream artifacts and steps that may be affected, enabling targeted re-validation

```
1.  Session start and use-case intake
2.  Collect requirements (full collection in V1; complete in V1+)
3.  Generate structured specifications (business_spec, technical_spec, target_output_spec)
4.  [Gate 1] Validate specifications with the user
5.  Design output schema (conditional -- typed structured-output use cases)
6.  Select GAIK modules and components
7.  Declare artifacts (ArtifactRegistry) and generate the executable JSON blueprint
8.  Generate visual workflow
    -- Mermaid diagram (V1)
    -- Read-only BPMN (V1+)

9.  [Gate 2] Validate workflow with the user
10. Create proof of concept (V1+)
11. [Gate 3] Run PoC, collect feedback, and refine prompts/schemas/parameters/components (V1+)
12. Generate the documentation suite (V1); build the final use-case package with tests + evaluation assets (V2)
```

Steps 1-12 correspond one-to-one with the detailed phases in Section 7 (7.1-7.12).

The workflow contains two required validation gates and one recommended gate:

- **Gate 1: Specification validation** -- user confirms the business and technical specification is correct.
- **Gate 2: Workflow validation** -- user confirms the generated workflow and selected components are appropriate.
- **Gate 3: PoC validation** (recommended, V1+) -- user confirms the proof of concept behaves sufficiently well to justify generating the full package.

## 7. Detailed Workflow

### 7.1 Phase 1: Session Start and Use-Case Intake

The wizard begins with two setup questions before any use-case content is collected:

1. **Output directory**: where should all generated files (blueprint, diagrams, PoC, package) be saved? The wizard does not save anything inside the GAIK repo by default. The user provides an absolute or relative path; the wizard creates the directory if it does not exist.
2. **Use-case description**: what business or operational task should the GenAI solution support?

Example opening:

```
Where would you like to save the generated files?
(Enter a folder path, e.g. ~/projects/my-use-case or C:\work\my-use-case)

What business or operational task should the GenAI solution support?
Please describe the current process, the input material, and the
output you want the system to produce.
```

The chosen output directory is stored in the blueprint under `package.output_dir` and used by all downstream steps. Files are laid out under it as follows:

```
<output_dir>/
    use_case.blueprint.json     <- executable blueprint (all releases)
    workflow.mmd                <- Mermaid diagram (V1+)
    workflow.bpmn               <- BPMN visual blueprint (V1+)
    poc/                        <- proof of concept (V1+, see Section 16)
    docs/                       <- documentation suite (V1+, see Section 18)
```

In V1, the documentation suite (Section 18) is generated into `<output_dir>/docs/`. In V2, the full use-case package (Section 17) is generated into the same `<output_dir>`, which becomes the package root. When the wizard is invoked from the CLI, the output directory can alternatively be provided via `--output-dir` to skip the interactive prompt.

The wizard then classifies the initial use case into a likely pattern: audio-to-structured-data, document-to-structured-data, RAG, document classification, report generation, or hybrid workflow.

### 7.2 Phase 2: Guided Requirement Collection

**V1 (full requirement collection)**: The wizard asks 7 targeted questions (see Section 5, V1) and proceeds to specification generation. Remaining fields are populated with clearly recorded assumptions.

**V1+ (complete)**: The wizard collects all fields from Section 8 through targeted questions, asking only the next relevant questions based on what is missing. It avoids presenting a long questionnaire at once.

Complete requirement collection covers:
- Use-case name and short description
- Domain and organizational context
- Current process without AI
- Pain points and expected value
- Intended users and reviewers
- Input artifacts and formats
- Target output artifacts and formats
- Required fields or sections in the output
- Language and terminology requirements
- Data sources and reference materials
- Integration needs
- Security, privacy, and compliance constraints
- Model provider preferences
- Human review needs
- Evaluation criteria
- Deployment and runtime expectations

For extraction use cases, the wizard also helps define the output schema: what fields are needed, what each means, whether required, what data type, and how missing or uncertain information should be represented.

### 7.3 Phase 3: Specification Generation

After enough information has been collected, the wizard generates three structured objects: `business_spec`, `technical_spec`, and `target_output_spec`. These are presented as a concise structured summary for the user to confirm.

### 7.4 Phase 4: Specification Validation (Gate 1)

The wizard presents the structured specification and asks for confirmation. The user can approve, edit, add missing details, or ask the wizard to make assumptions explicit. The wizard does not proceed to component selection until the specification is confirmed.

### 7.5 Phase 5: Schema Design (conditionally invoked)

`SchemaDesigner` is conditionally invoked when the use case requires a typed structured output. Its position in the pipeline depends on what is known at that point:

**Invoked before component selection** when the target output schema is fully defined by the specification (the user knows exactly which fields they need regardless of how they are extracted). In this case `SchemaDesigner` produces the schema first; `ComponentSelector` then chooses a component that can consume it.

**Invoked after initial component selection** when the selected workflow determines schema requirements. For example:
- `VisionExtractor` uses the schema directly in a single API call -- schema design must follow component selection so the generated schema artifacts are packaged and referenced in the format expected by the selected runtime component.
- `MultimodalParser + DataExtractor` may need separate parsing prompts and extraction schema -- the two-step structure affects schema granularity.
- RAG workflows typically do not require a structured output schema at all -- this phase is skipped.

In all cases, `SchemaDesigner` takes field definitions from `SpecificationBuilder`, invokes the GAIK `SchemaGenerator` component, and produces:

- `output_schema.py` -- a typed Pydantic model defining fields, types, required flags, and allowed values
- `requirements.json` -- parsed field specifications used by `DataExtractor` or `VisionExtractor` at runtime

The wizard presents the generated schema to the user for confirmation before proceeding. The confirmed schema is recorded in the blueprint under `schemas` and referenced by downstream workflow steps.

### 7.6 Phase 6: Component Selection

Selection is **agent-driven** (see Section 3.4): the agent reads the registry fields directly and reasons from them. It does not score components or look up a preset list, and it does not run a deterministic pattern classifier -- the agent owns pattern interpretation itself. Two deterministic aids support it: the transformation-chain scaffolds and the module-first map (both reference data), and the validator as the safety net.

**Step 1: Infer the transformation chain**

The agent derives the ordered sequence of data states between input and final output. Canonical scaffolds for the common patterns are provided as reference data (the agent may adapt them). Example for incident reporting:

```
audio -> raw transcript -> enhanced transcript -> extraction schema -> structured JSON -> validated output -> approved report
```

**Step 2: Map transformations to components or modules**

Apply the module-first rule: check whether a single GAIK software module covers the full chain (its `input_artifact_types`/`output_artifact_types` match the use case). If yes, select it. If not, map each transformation step to the component that produces it, choosing between candidates by reading each entry's `best_for` and `known_limitations`:

| Transformation | Component |
|---------------|-----------|
| audio -> raw transcript | `Transcriber` |
| raw transcript -> enhanced transcript | `TranscriptEnhancer` |
| field definitions -> typed schema | `SchemaGenerator` |
| enhanced transcript + schema -> structured JSON | `DataExtractor` |
| structured JSON -> validated output | `LLMJudge` |
| validated output -> approved report | human review step |

**Step 3: Declare artifacts**

Pass the transformation chain to `ArtifactRegistry`. Each link in the chain becomes a typed artifact that steps consume and produce:

```
"incident_audio" -> "raw_transcript" -> "enhanced_transcript" -> "incident_report_json" -> "approved_report"
```

The wizard then provides a short selection rationale and a traceability table linking each selected component to a requirement.

Examples:
- Audio input + structured JSON output -> `AudioToStructuredData`
- PDF/DOCX input + structured JSON output -> `DocumentsToStructuredData`
- Document collection + question answering -> `RAGWorkflow`
- Complex visual documents -> `MultimodalParser` or `VisionExtractor`
- Database question answering -> `PostgresAgent`
- Output quality validation -> `LLMJudge` or `ExtractionEvaluator`

### 7.7 Phase 7: Artifact Declaration and JSON Blueprint Generation

The `ArtifactRegistry` agent takes the transformation chain produced in Phase 6 and declares each link as a typed, named artifact. Workflow steps then reference these artifact IDs rather than passing data implicitly. This is what makes the transformation chain machine-checkable: the validator can verify that every step receives an artifact of the right type and that no artifact is consumed before it is produced.

Example artifact chain for incident reporting:

```
incident_audio (user_upload)
    -> raw_transcript (generated, produced_by: transcribe_audio)
    -> enhanced_transcript (generated, produced_by: enhance_transcript)
    -> incident_report_json (generated, final_output: true, produced_by: extract_report_fields)
    -> approved_report (generated, final_output: true, produced_by: human_review)
```

The wizard creates the executable JSON blueprint after all artifacts are declared.

### 7.8 Phase 8: Visual Workflow Generation

**V1**: The JSON blueprint drives generation of the **BPMN visual blueprint** (`workflow.bpmn`) — a standards-based business-process model for stakeholder review and governance — and the Mermaid diagram for quick technical validation. Both are linked to the JSON; changes are made in the JSON and the diagrams are regenerated.
**V2**: The BPMN canvas becomes directly editable; changes are converted to JSON change operations and the BPMN is regenerated from the updated JSON (see Section 5, V2).

### 7.9 Phase 9: Workflow Validation (Gate 2)

The user reviews the visual workflow and the component-selection summary. Changes are applied to the JSON blueprint first; the visual workflow is regenerated from the updated JSON. In V2, users may edit through the BPMN canvas, step configuration panel, or wizard chat.

### 7.10 Phase 10: Proof-of-Concept Creation (V1+)

The wizard generates a minimal proof of concept (see Section 16). The PoC uses either user-provided input data or synthetic sample data and focuses on the smallest useful pipeline that demonstrates the main value of the use case.

After generation, the wizard prints a structured handoff message in the conversation to guide the user through running the PoC:

```
Your PoC has been generated at: ~/projects/my-use-case/poc/

To run it:
  1. Install dependencies:
         pip install -r requirements.txt
  2. Set up your environment:
         cp .env.example .env
         -- then open .env and fill in your API key
  3. Add a sample input file:
         place it in poc/sample_input/  (expected format: .wav audio file)
  4. Run the pipeline:
         python run_poc.py
  5. Inspect the output:
         check poc/output/ for the generated result

When you are ready, paste the output here or describe what you see.
I will help you interpret the result and refine the prompts, schema,
or model settings if needed.
```

The handoff message is use-case-specific: it shows the actual input format, expected file name, and output location from the blueprint rather than generic placeholders.

### 7.11 Phase 11: PoC Validation and Refinement (V1+)

The user runs the PoC following the handoff message from Phase 10 and shares the output with the wizard -- either by pasting the result directly into the conversation or by describing what they observed. The wizard then:

1. **Interprets the output** -- identifies whether the extraction, transcription, classification, or retrieval result looks correct, incomplete, or wrong.
2. **Diagnoses issues** -- maps observed problems to likely causes: prompt too vague, schema field missing, wrong model temperature, parser not handling the document layout, validation threshold too strict.
3. **Proposes specific changes** -- each change is expressed as a blueprint diff (component parameter, prompt content, schema field, validation rule) and shown to the user for approval before being applied.
4. **Regenerates affected outputs** -- after approval, the wizard updates the blueprint and regenerates only the affected PoC files (prompt file, schema file, config), then instructs the user to re-run.

This loop repeats until the user is satisfied with the PoC output or explicitly decides to proceed to full package generation. All approved refinements are recorded in the blueprint `change_log`.

### 7.12 Phase 12: Documentation Suite (V1) and Full Package (V2)

After the PoC is validated, the wizard generates the **documentation suite** from the validated blueprint into `<output_dir>/docs/` (GenAI product canvas, technical specification, user guide, developer guide, evaluation plan -- see Section 18). In **V2**, the wizard additionally generates the full use-case package (see Section 17), which incorporates these documents under its `docs/` folder.

## 10. JSON Blueprint Design

The JSON blueprint is the executable source of truth. It should be generated after specification validation and updated after each major change.

### 10.1 Required Top-Level Sections

```json
{
  "blueprint_version": "1.0",
  "metadata": {},
  "use_case": {},
  "business_spec": {},
  "technical_spec": {},
  "target_output_spec": {},
  "assumptions": [],
  "artifacts": {},
  "inputs": {},
  "outputs": {},
  "schemas": {},
  "components": {},
  "workflow": {},
  "prompts": {},
  "models": {},
  "validation": {},
  "evaluation": {},
  "governance": {
    "data_handling": {}
  },
  "runtime": {},
  "package": {},
  "visualizations": {},
  "traceability": [],
  "change_log": []
}
```

> **Note**: `bpmn_mapping` section is added in V2 only.

> **Artifact authority**: `artifacts` is the canonical registry of all data objects in the pipeline. `inputs` and `outputs` are optional business-facing summaries for UI grouping and generated documentation (e.g. the GenAI product canvas); they are not authoritative. BlueprintValidator must derive artifact existence, type, and flow from `artifacts`, not from `inputs` or `outputs`. Future implementers should not add artifact definitions to `inputs`/`outputs` that do not also appear in `artifacts`.

> **`target_output_spec`**: holds the structured-output field definitions described in Section 8.3 (field names, types, required flags, allowed values, missing-value policy). It is the input that `SchemaDesigner` (Section 7.5) consumes to generate `output_schema.py` and `requirements.json`. For RAG or other non-extraction use cases it may be empty or omitted.

> **`visualizations`**: holds the file paths of the generated visual workflows (`workflow.mmd` in V1, `workflow.bpmn` in V1+) relative to the output directory. It is populated by `WorkflowVisualizer` as a convenience index; the diagrams themselves are always regenerated from `artifacts` and `workflow`, so this section is not authoritative.

### 10.2 Assumptions

The `assumptions` field is a first-class top-level section. Every time the wizard proceeds with incomplete information it records a structured assumption entry. This makes assumptions visible, queryable, and resolvable -- rather than buried in prose notes.

```json
"assumptions": [
  {
    "id": "assumption_001",
    "text": "Input documents are primarily PDF files with text-based content, not scanned images.",
    "status": "unconfirmed",
    "impact": "component_selection",
    "recorded_by": "ComponentSelector",
    "recorded_at": "2026-06-04T09:00:00Z"
  },
  {
    "id": "assumption_002",
    "text": "Human review is required before the report is submitted to the safety database.",
    "status": "confirmed",
    "impact": "workflow_design",
    "recorded_by": "SpecificationBuilder",
    "recorded_at": "2026-06-04T09:01:00Z"
  }
]
```

The `status` field may be `"unconfirmed"`, `"confirmed"`, or `"overridden"`. BlueprintValidator should warn when a high-impact decision (component selection, human-review gate, security constraint) rests on an `"unconfirmed"` assumption. The wizard should surface unconfirmed assumptions during dialogue and prompt the user to resolve them before production packaging.

### 10.3 Artifact Declarations (First-Class Objects)

All artifacts must be declared before they are referenced by workflow steps. Artifacts have a `source` property that distinguishes user-provided inputs from generated intermediates, and a `final_output` flag that marks deliverables intended for the user or downstream system.

**User-provided input artifacts:**
```json
"source_audio": {
  "type": "audio",
  "source": "user_upload",
  "optional": false
},
"incident_photo": {
  "type": "image",
  "source": "user_upload",
  "optional": true
}
```

**Generated intermediate artifacts:**
```json
"raw_transcript": {
  "type": "text",
  "source": "generated",
  "optional": false,
  "final_output": false,
  "produced_by": "transcribe_audio"
},
"enhanced_transcript": {
  "type": "text",
  "source": "generated",
  "optional": false,
  "final_output": false,
  "produced_by": "enhance_transcript"
}
```

**Final output artifacts:**
```json
"structured_json": {
  "type": "structured_json",
  "source": "generated",
  "optional": false,
  "final_output": true,
  "produced_by": "extract_report_fields",
  "schema_ref": "schemas/output_schema.py"
}
```

This separation makes BlueprintValidator's job unambiguous: `optional` on an input artifact means the user may omit it; `optional: false` on a generated artifact means the step that produces it must always run.

The Pydantic validator should enforce the following conditional rules (the JSON Schema cannot express these constraints directly):

**Field defaults:**
- `final_output` defaults to `false` if omitted.
- `optional` is **required** for all artifacts regardless of source. There is no default -- requiring an explicit value prevents silent misclassification.

**Conditional rules:**
- If `source == "generated"`, then `produced_by` is **required** and must reference an existing step ID.
- If `source == "user_upload"`, then `produced_by` must be **absent** (it has no producing step).
- If `final_output == true`, the artifact must meet at least one of the following conditions: (1) produced by a terminal delivery step (a step with no downstream consumers other than storage, export, or reporting steps); (2) produced by a human-review step; or (3) explicitly marked with `"externally_visible": true` to indicate it is an externally consumed output even when later evaluation or reporting steps also read it. This prevents evaluation pipelines from incorrectly disqualifying valid final artifacts.

### 10.4 Blueprint Rules

1. Every workflow step must have a unique `id`.
2. Every step must declare its inputs and outputs, referencing artifact IDs from `artifacts`.
3. Every component must exist in the component registry or be marked as custom.
4. Every prompt used by a component must have a file path or inline template.
5. Every schema used by a component must have a file path or inline definition.
6. Output artifacts that overwrite an existing artifact must be flagged `"overwrite": true`.
7. Every external dependency must be declared.
8. Every assumption must be recorded.
9. Every user-approved decision must be marked as approved.
10. Visual workflow files must be generated from the blueprint, not edited as the source of truth (V1-V1).
11. Runtime code must be generated from the blueprint.
12. Workflow graph must be acyclic unless loops are explicitly declared with `max_iterations` or `loop_condition_ref`.
13. At least one terminal step must produce a final output artifact.
14. `governance.data_handling.contains_personal_data` and `output_sensitivity` must not be `"unknown"` in production packages (PackageBuilder blocks on these).
15. In V2 only: every BPMN element maps to a JSON object through a stable identifier; every visual or conversational edit is converted to a validated JSON change operation before being saved; after each approved edit the BPMN model is regenerated from the updated JSON.

### 10.5 Blueprint Diffing

A structured diff format is used when BlueprintValidator runs targeted re-validation on affected steps:

```json
{
  "change_id": "change_005",
  "changed_by": "user_via_chat",
  "timestamp": "2026-06-04T09:12:00Z",
  "path": "workflow.steps[2].component",
  "old_value": "PyMuPDFParser",
  "new_value": "MultimodalParser",
  "reason": "User requested better table extraction for complex layouts",
  "validation_status": "pending"
}
```

### 10.6 Governance -- data_handling Section

Every blueprint must include:

```json
"governance": {
  "data_handling": {
    "external_model_api_allowed": true,
    "local_processing_required": false,
    "stores_input_data": false,
    "stores_outputs": true,
    "retention_policy": "not_specified",
    "contains_personal_data": "unknown",
    "output_sensitivity": "unknown",
    "audit_log_required": false
  }
}
```

- `contains_personal_data` and `output_sensitivity` are recorded as descriptive metadata. The wizard surfaces `"unknown"` values as open questions and encourages the user to resolve them, but they do **not** block any stage.
- `audit_log_required` defaults to `true` for safety, HR, finance, and legal use cases.
- These fields also drive BPMN governance annotations (PII / sensitivity / audit-log).

## 13. Component Registry

The wizard needs a component registry to make repeatable component-selection decisions. The registry is stored as JSON or YAML and loaded at runtime.

### 13.1 Registry Fields

Each registry entry includes:

```json
{
  "id": "audio_to_structured_data",
  "name": "AudioToStructuredData",
  "type": "software_module",
  "input_artifact_types": ["audio"],
  "output_artifact_types": ["structured_json"],
  "knowledge_processes": ["knowledge_capture"],
  "uses_components": [
    "Transcriber", "TranscriptEnhancer", "SchemaGenerator", "DataExtractor"
  ],
  "required_parameters": ["schema_ref", "requirements_ref"],
  "optional_parameters": ["language", "transcription_model", "extraction_model"],
  "supported_providers": ["openai", "azure_openai", "claude", "google"],
  "cost_relevant_parameters": ["transcription_model", "extraction_model"],
  "quality_tradeoffs": {
    "speed_vs_accuracy": "2-pass enhancement adds ~60s for typical 5-min recording",
    "cost_sensitivity": "medium -- two LLM calls per document",
    "degrades_on": ["very_noisy_audio", "heavily_accented_speech_without_domain_tuning"]
  },
  "known_limitations": [
    "requires audio input; cannot process text-only input without bypassing Transcriber",
    "TranscriptEnhancer is tuned for Finnish; other languages require prompt customization"
  ],
  "minimum_viable_config": {
    "schema_ref": "schemas/output_schema.py",
    "requirements_ref": "schemas/requirements.json"
  },
  "upgrade_path": null,
  "downgrade_path": "Transcriber only (no structured extraction)",
  "best_for": [
    "spoken_report_to_structured_form",
    "voice_note_to_json",
    "incident_audio_to_report"
  ],
  "example_blueprint_steps": [
    {
      "id": "transcribe_audio",
      "component": "Transcriber",
      "inputs": ["source_audio"],
      "outputs": ["raw_transcript"]
    },
    {
      "id": "extract_fields",
      "component": "DataExtractor",
      "inputs": ["raw_transcript"],
      "outputs": ["structured_json"],
      "parameters": {
        "schema_ref": "schemas/output_schema.py",
        "requirements_ref": "schemas/requirements.json"
      }
    }
  ],
  "source_path": "implementation_layer/src/gaik/software_modules/audio_to_structured_data/",
  "import_path": "gaik.software_modules.audio_to_structured_data",
  "example_script_path": "implementation_layer/examples/software_modules/audio_to_structured_data/",
  "readme_path": "implementation_layer/src/gaik/software_modules/audio_to_structured_data/README.md"

```

> **No `selection_rules` field.** Selection is agent-driven (Section 3.4): the agent reads `input_artifact_types`, `output_artifact_types`, `best_for`, and `known_limitations` and reasons from them. There are no per-entry scoring rules to author or maintain -- adding a component is a single registry entry. The registry is validated against `component_registry.schema.json` on load. (If a new component covers a use-case pattern end-to-end as a module, it is also added to the module-first map so that rule prefers it.)

### 13.2 Module Composition: `uses_components`

Software module entries include a `uses_components` field listing the internal building blocks the module orchestrates. This lets the wizard explain what a module contains and — when the user needs custom control over individual steps — expand it into its constituent components without re-querying the source.

```json
"uses_components": ["Transcriber", "TranscriptEnhancer", "SchemaGenerator", "DataExtractor"]
```

`ComponentSelector` uses this field to:
- Show the user what steps are hidden inside a module before they commit to it
- Identify which individual components to fall back to if the module does not fully match the use case (e.g. user wants to skip `TranscriptEnhancer` for a non-Finnish language)
- Populate the `BlueprintBuilder` step list when the module is decomposed into explicit workflow steps

Software component entries do not have a `uses_components` field -- they are leaf-level and have no sub-components.

### 13.3 Initial Registry Categories

| Category | Example Capabilities |
|----------|---------------------|
| Transcription | Audio or video to transcript |
| Transcript enhancement | Correct and normalize transcript text |
| Document parsing | Convert PDF, DOCX, or scanned documents into text or markdown |
| Vision parsing | Interpret charts, figures, layouts, scanned pages, and images |
| Schema generation | Generate structured schemas from field requirements |
| Data extraction | Extract structured data from text, documents, or transcripts |
| Document classification | Assign documents to categories using natural-language definitions |
| RAG | Parse, embed, store, retrieve, and answer with references |
| Validation | Check output quality, hallucination, completeness, and consistency |
| Evaluation | Run field-level, semantic, or RAG evaluation over test datasets |

### 13.4 Component Information Retrieval Model

The wizard's information needs grow across releases. Three mechanisms cover the full range, applied at different layers:

| Mechanism | What it answers | Used from |
|-----------|----------------|-----------|
| **Registry JSON** | What does this component do? What are its input/output types, params, `best_for`, and `known_limitations`? | V1+ |
| **Reference cards** | How do I call this component? What is its import path, constructor signature, return type, and behaviour-changing options? | V1+ (hand-maintained, made complete + option-aware in V1) |
| **Graphify graph (cards embedded)** | What relates to this component? Which modules use it? Which examples reference it? Queried as a unified graph. | V2 |

#### V1: Registry as Index, Files as Content

The registry provides selection-time information. When PoCScaffolder or PackageBuilder need implementation details, they read the files referenced by the selected components' `readme_path`, `example_script_path`, and `source_path`. The `import_path` field provides the Python import without requiring a file read. No additional infrastructure is needed.

#### V2: Reference Cards Embedded in the Graphify Graph

Reference cards are generated first from the component source code, READMEs, and example scripts. They capture the stable API contract for each component:

```json
{
  "id": "vision_extractor",
  "class_name": "VisionExtractor",
  "import_path": "gaik.software_components.vision_extractor",
  "constructor_params": {
    "model_provider": "openai | claude | google",
    "reasoning_effort": "low | medium | high",
    "use_azure": "bool"
  },
  "main_method": "extract",
  "method_params": {
    "file_paths": "list[str]",
    "task": "str",
    "schema_dir": "str | None",
    "include_verification": "bool"
  },
  "returns": "VisionExtractionResult",
  "minimal_example": "from gaik.software_components.vision_extractor import VisionExtractor\nextractor = VisionExtractor(model_provider='openai', use_azure=True)\nresult = extractor.extract(file_paths=['doc.pdf'], task='Extract invoice fields')\nprint(result.data)"
}
```

Once generated, reference cards are **included as nodes in the Graphify knowledge graph**. This means the wizard queries a single unified graph rather than two separate systems. A query such as `graphify query "how do I call VisionExtractor"` returns both the card data (import path, constructor, return type) and the relationship data (which modules use it, which examples reference it, which artifact types it produces) in a single pass.

**Information flow for V2:**

```
Source code + READMEs + examples
    --> [card generation step]
    --> reference_cards/*.json

reference_cards/*.json + source graph
    --> [graphify update]
    --> graphify-out/graph.json  (unified graph with card nodes)

Wizard agents:
    ComponentSelector   --> graphify query (relationships + card summaries)
    SchemaDesigner      --> graphify query (component schema requirements)
    BlueprintBuilder    --> graphify query (card API contracts)
    PoCScaffolder       --> graphify query (card) + raw example file (full code)
    PackageBuilder      --> graphify query (card) + raw example file (full code)
```

**Why PoCScaffolder and PackageBuilder still read raw files:** the card stores a `minimal_example` (a short importable snippet). For full PoC and package generation, the scaffolder needs the complete example script with configuration, error handling, and sample data paths. The graph node contains the file path; the scaffolder reads the file. The graph gives the pointer; the file gives the content.

**Layered retrieval model across all releases:**

| Agent | V1-V1 | V2 |
|-------|--------|--------|
| `ComponentSelector` | Registry fields (types, `best_for`, `known_limitations`) + reference-card options (V1) | Registry fields + Graphify queries (relationships) |
| `SchemaDesigner` | Registry | Graphify (schema requirements per component) |
| `BlueprintBuilder` | Registry + `example_blueprint_steps` + reference cards | Registry + Graphify (card API contracts) |
| `PoCScaffolder` | `readme_path` + `example_script_path` + reference cards | Graphify card + raw example file |
| `PackageBuilder` | `readme_path` + `example_script_path` | Graphify card + raw example file |

## 14. Component Selection Guidance

Selection is agent-driven (Section 3.4): the agent reads the registry fields and reasons from them. It is **not** a deterministic rule engine. The only deterministic elements are the module-first rule and the `BlueprintValidator` safety net; everything else is the agent's interpretation. The agent also records why a component was *not* selected when there are plausible alternatives.

The table below is **guidance the agent uses, not a lookup it is bound to** -- common requirement patterns and the typical selection. The agent may deviate when the use case calls for it (and the validator will still enforce type compatibility).

| Requirement Pattern | Typical Selection |
|--------------------|----------------------|
| Audio input + structured JSON output | `AudioToStructuredData` |
| Audio input + transcript output only | `Transcriber`, optionally `TranscriptEnhancer` |
| PDF/DOCX input + structured JSON output | `DocumentsToStructuredData` |
| Scanned or visually complex documents | `MultimodalParser`, `VisionPlusParser`, or `VisionExtractor` |
| Images or blueprints to structured output | `VisionExtractor` or vision parser + extractor |
| Document collection + question answering | `RAGWorkflow` |
| Search over video transcripts | `Transcriber` + RAG components |
| Document type detection | `DocumentClassifier` |
| Natural-language database questions | `PostgresAgent` |
| Field-level extraction quality metrics | `ExtractionEvaluator` |
| RAG quality metrics | `RAGEvaluator` |
| Hallucination or faithfulness checking | `LLMJudge` or `LLMJudgePanel` |

The PoC supports two execution modes:

1. **User-data mode**: the user provides real sample files placed in `sample_input/`.
2. **Synthetic-data mode**: the wizard generates small artificial examples for testing the pipeline and places them in `sample_input/` automatically.

The PoC writes all outputs to the `output/` folder and avoids modifying external systems.

**Generated `README.md`**

The wizard generates a use-case-specific `README.md` -- not a generic template. It contains:

- Prerequisites: Python version and `pip install -r requirements.txt`
- Environment setup: which variables to set in `.env` and where to get the values (e.g. Azure API key, endpoint)
- Input instructions: exact file name, format, and location expected by `run_poc.py` for this use case
- Run command: the exact command to execute
- Expected output: what the result file looks like and where it is written
- Adjustment guide: which file to edit for each type of change -- prompt wording (`prompts/`), output fields (`schemas/`), model or temperature (`config.yaml`)

This means a user who has never seen the wizard before can pick up the generated folder and run the PoC without returning to the wizard conversation.

## 20. Security, Privacy, and Governance

Every blueprint includes a `governance.data_handling` section (see Section 10.6). Default rules:

1. Do not automatically submit generated outputs to external systems without user approval.
2. Include human review for high-impact or safety-related outputs.

6. Record whether local processing is required.
7. Record data-retention assumptions.

## 23. Implementation Design

The wizard is implemented as a single consolidated package at `implementation_layer/solution_wizard/`. The SKILL.md (the conversational orchestration layer) and all Python implementation code (validators, scaffolders, generators) live together in one location, versioned and deployed as a unit.

### 23.1 Two-Layer Architecture

The wizard has two layers inside the same package:

| Layer | What it contains | Role |
|-------|-----------------|------|
| **SKILL.md** | Conversation flow, question phrasing, phase sequencing, script invocation calls | Orchestration -- the pilot |
| **Python scripts and modules** | Blueprint validation, registry lookup, Mermaid/BPMN generation, PoC and package scaffolding, change operations | Implementation -- the aircraft |

The SKILL.md calls the Python scripts by relative path. The scripts are independently runnable from the command line, callable from CI, and testable without a Claude session.

The proposal-validation loop is enforced at the code level -- the LLM may draft proposals but no change is persisted until validation passes and, where required, the user approves:

```
LLM proposes -> validate_blueprint.py checks -> User approves -> Blueprint updates
```

## 25. Final Validation Checklist

Before a generated package is delivered:

1. JSON blueprint validates against schema.
2. All declared artifacts have valid types.
3. All selected components exist in the registry.
4. All workflow steps have declared inputs and outputs referencing artifact IDs.
5. No artifact is produced more than once without `"overwrite": true`.
6. All prompts referenced by the blueprint exist.
7. All schemas referenced by the blueprint exist.
8. Workflow graph is acyclic (or loops have `max_iterations` / `loop_condition_ref`).
9. At least one terminal step produces a final output artifact.
10. The PoC runs with sample or synthetic data (V1+).
11. Output validates against the target schema.
12. Human review step exists where required.
13. No real API keys or secrets are included.
14. `governance.data_handling` is recorded; `"unknown"` values for `contains_personal_data` / `output_sensitivity` are surfaced to the user (descriptive metadata, non-blocking).
15. Component-option settings are recorded in `workflow.steps[].parameters`, and no sub-component duplicates a capability already provided by an option or selected module (V1+).
16. README explains how to install and run the package.
17. Evaluation script exists or evaluation limitations are documented.
18. Mermaid diagram is generated from the executable blueprint (V1+).
19. BPMN workflow file is generated from the JSON blueprint (V1+).
20. Documentation suite is generated from the validated blueprint (V1+); full package structure follows the standard layout (V1+).

**Additional V2 checks**:
- All BPMN workflow elements are linked to JSON blueprint elements through stable identifiers.
- All user edits made through BPMN, configuration panels, or chat are recorded in the blueprint change log.
- The final BPMN workflow has been regenerated from the validated JSON blueprint.

## 26. Summary

The GAIK Solution Configuration Wizard is a structured agent that turns a business use-case idea into a validated and executable GenAI solution package. It collects requirements, generates specifications, selects components, creates an executable JSON blueprint, produces visual workflows, builds a proof of concept, and generates a complete use-case package.

The two-release plan delivers usable value now and preserves a clear path for future extension:

- **V1 (current)** delivers full requirement collection (with a completeness gate), component-option awareness, reference-card completeness, read-only BPMN visual blueprint, PoC scaffolding, and the use-case documentation suite — all in a single-agent `SKILL.md` with no sub-agents required.
- **V2 (future)** adds full package generation, reference-card auto-generation + Graphify integration for component intelligence, and interactive BPMN editing with synchronized BPMN-JSON validation.

The solution is built on two complementary blueprints. The **JSON blueprint** is the executable source of truth: machine-readable, version-controlled, and the artifact that drives every downstream generation step. The **BPMN visual blueprint** is the business-process view: a standards-based model that makes the solution legible to stakeholders, supports process review and governance, and — in V2 — becomes directly editable with changes propagated back to the JSON. Neither blueprint diminishes the other; they serve different audiences and different purposes in the same solution lifecycle.

The staged agent architecture (RequirementCollector -> SpecificationBuilder -> SchemaDesigner -> ComponentSelector -> ArtifactRegistry -> BlueprintBuilder -> BlueprintValidator -> WorkflowVisualizer -> PoCScaffolder -> PackageBuilder) ensures no single agent becomes too large to validate, and each stage can be tested and improved independently.
