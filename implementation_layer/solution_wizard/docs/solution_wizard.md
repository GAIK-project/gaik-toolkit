Version 1.0 -- June 2026

Two-release plan: **V1** (current, §§1–23) complete requirements + PoC + BPMN + documentation · **V2** (planned, §24) full package + production UI + security

## Executive Summary

The GAIK Solution Configuration Wizard is an agentic assistant that helps users design, validate, prototype, and package GenAI use cases using the GAIK toolkit. It translates a user's business problem into a structured specification, selects suitable GAIK software components or software modules, generates an executable JSON blueprint, creates a visual workflow for review, builds a minimal proof of concept, and then expands the proof of concept into a complete executable use-case package.

The wizard is intended for users who may understand their business problem but may not know which GenAI components, prompts, schemas, parsers, transcribers, RAG modules, validators, or evaluation tools are required. It acts as a bridge between business-level use-case thinking and technical implementation. The main output is a reusable package that contains code, prompts, schemas, workflow files, documentation, tests, and evaluation assets.

The wizard produces two complementary blueprints that serve different but equally important roles:

**The JSON blueprint** is the executable source of truth. It captures the complete technical configuration of the use case: input and output artifacts, selected GAIK components and their options, workflow steps, schemas, prompts, model settings, validation gates, evaluation plan, and deployment assumptions. It is the artifact that drives code generation, validation, PoC scaffolding, and documentation.

**The BPMN visual blueprint** is the business-process view. It is a standards-based BPMN 2.0 model — with swimlanes for each stakeholder role, typed tasks (user tasks, automated AI steps, human-review tasks), gateways, data objects, data stores, and message flows — that makes the solution legible to business analysts, domain experts, and decision-makers. It is generated from the JSON blueprint and linked to it element-by-element through stable identifiers (`visualizations.bpmn_mapping`), so every business-process element traces back to its technical counterpart.

This document describes V1 (current release) in full. V2 (planned) is covered in Section 24.

## 1. Purpose of the Wizard

The purpose of the Solution Configuration Wizard is to make GAIK use-case development more systematic, repeatable, and accessible. Instead of manually deciding which components to use and how to connect them, the user can describe the target use case in natural language. The wizard then guides the user through a structured process that results in an executable configuration and a working package.

The wizard supports three main goals:

1. **Use-case discovery and clarification**: help the user define what problem the solution should solve, who will use it, what inputs and outputs are involved, and what constraints must be respected.
2. **Solution configuration**: select the required GAIK software modules and lower-level building blocks, define prompts and schemas, and generate an executable JSON blueprint.
3. **Use-case implementation support**: create a proof of concept, validate the result with the user, and then generate a complete use-case package with code, tests, evaluation scripts, documentation, and workflow artifacts.


---

## 2. Scope

The wizard focuses on GenAI use cases that can be implemented using GAIK's existing software components or software modules. It supports at least the following use-case families:

- Audio or video to structured data
- Document to structured data
- Complex document parsing and extraction
- Vision-based extraction from images, scanned documents, charts, or technical drawings
- Retrieval-augmented generation over document collections
- Conversational access to internal knowledge
- Report, summary, or proposal generation
- Document classification
- Text-to-SQL or question answering over structured databases
- Validation and evaluation of generated or extracted outputs

The wizard also supports hybrid use cases -- for example, audio transcription followed by structured extraction and report generation, or document parsing followed by RAG-based question answering.

**Each scope entry names a pipeline pattern, not a single component.** "Audio or video to structured data" implies a sequence that may involve Transcriber, TranscriptEnhancer, SchemaGenerator, DataExtractor, and a validation step -- all wired together through typed intermediate artifacts. The wizard resolves these chains automatically: it first checks whether a single GAIK software module covers the needed workflow; if not, it composes a custom pipeline from individual software components. A user who describes an incident reporting system will get a 5-6 component pipeline, not a single black-box call.

## 3. Core Principles

### 3.1 Artifact-Driven Interaction

Every phase should produce an artifact that can be inspected, saved, edited, reused, or versioned. The conversation is only the interface. The durable outputs are specifications, blueprints, schemas, prompts, workflow files, code, tests, and documentation.

### 3.2 JSON as the Executable Source of Truth

The JSON blueprint is the executable source of truth; the BPMN is derived from it. The JSON stores what the system does; the BPMN communicates how the business process works. Each is in the format most appropriate for its audience.

### 3.3 Human Validation Before Build

The wizard should not move directly from a short use-case description to code generation. It should first create a structured specification, ask the user to confirm it, generate a workflow blueprint, ask the user to validate it, and only then create the proof of concept or final package.

### 3.4 Agent-Driven Component Selection (Module-First)

Component selection uses the **same logic in every release (V1)**. The agent selects components by reading the registry fields directly -- `input_artifact_types`, `output_artifact_types`, `best_for`, and `known_limitations` -- and reasoning from them. There are no scoring tables, score boosts, or `selection_rules` files: those would have to be hand-maintained for every new component, whereas a registry entry already carries everything needed to choose.

Two deterministic rules constrain that reasoning:

1. **Module-first**: when a single GAIK software module already covers the needed workflow end-to-end (its input/output artifact types match the use case), the agent selects that module first. Lower-level building blocks are selected when the use case needs a custom pipeline, additional validation, special parsing, or non-standard orchestration.
2. **Validator as safety net**: every selection is checked by `BlueprintValidator` (component exists, artifact-type compatibility, required parameters present). A wrong selection is caught there, not by a scoring heuristic.

Adding a new component is therefore a one-file change: add its registry entry (plus its reference card).

### 3.5 Traceability

Every selected component should be linked to the requirement that caused it to be selected. This makes the generated solution easier to explain, debug, audit, and improve.

### 3.6 Skill as Orchestration Layer, Code as Implementation Layer

The Claude Skill (`SKILL.md`) is the user-facing interaction and orchestration layer. It manages conversation flow, asks follow-up questions, drafts specifications, explains tradeoffs, and calls implementation scripts. It is the pilot, not the aircraft.

All durable logic -- schema validation, component registry lookup, blueprint validation, Mermaid generation, PoC scaffolding, package structure -- lives in normal Python code outside the Skill instructions. This ensures that:

- Individual validators and scaffolders are unit-testable
- The wizard can be called from a CLI, CI pipeline, or future web UI without Claude
- Logic is versioned as code, not embedded in a prompt
- Each script can be developed and improved independently

The Skill orchestrates by calling scripts: `validate_blueprint.py`, `generate_mermaid.py`, `scaffold_poc.py`, `scaffold_package.py`. The scripts do the work; the Skill connects them.

### 3.7 Safe Defaults

The wizard should use conservative defaults, especially for privacy, human review, evaluation, data retention, and automatic submission to external systems. For example, any workflow that produces safety, legal, HR, financial, or operationally sensitive outputs should include a human review step by default.

### 3.8 Staged Agent Architecture

The wizard is experienced as one assistant but designed as a pipeline of specialized stages. Each stage receives the current blueprint JSON and returns an updated blueprint or a structured diff. This keeps any single stage from accumulating too much context, and allows each to be tested and replaced independently.

```
RequirementCollector
    -> SpecificationBuilder      (includes RequirementCompletenessChecker)
    -> SchemaDesigner            (conditionally: before or after ComponentSelector -- see Section 7.5)
    -> ComponentSelector
    -> ArtifactRegistry
    -> BlueprintBuilder
    -> BlueprintValidator        (must pass before visualization)
    -> WorkflowVisualizer        (Mermaid in V1+; BPMN in V1+)
    -> PoCScaffolder             (V1+)
    -> PackageBuilder            (V2)
```

In V1 all stages are realized as a **single `SKILL.md` orchestrator** that runs them as sequential phases, calling deterministic Python scripts (`validate_blueprint.py`, `generate_mermaid.py`, `generate_bpmn.py`, `scaffold_poc.py`, `check_requirements.py`, `generate_docs.py`). The whole flow fits comfortably in one context window. Stages that are deterministic (module-first rule, ArtifactRegistry, BlueprintValidator, WorkflowVisualizer) live in code; the interpretive stages (RequirementCollector, SpecificationBuilder) are roles the single agent plays.

Each stage receives `use_case.blueprint.json` and returns a complete updated blueprint or a structured diff. No change is persisted until it passes validation and, where required, user approval.

## 4. Key Concepts

### 4.1 Target Output Schema

The target output schema defines the structured artifact that the system should produce. For extraction use cases, this may be a Pydantic model or JSON Schema that defines fields, types, descriptions, required fields, confidence scores, and validation rules.

### 4.2 Software Module vs Software Component

The wizard distinguishes two levels of GAIK capability:

| Type | Definition | Selection rule |
|------|-----------|---------------|
| **Software module** | A complete workflow-level capability that packages multiple components into a single, reusable pipeline (e.g. `AudioToStructuredData`, `DocumentsToStructuredData`, `RAGWorkflow`) | Select first if it covers the use case end-to-end |
| **Software component** | A lower-level building block with a single well-defined responsibility (e.g. `Transcriber`, `TranscriptEnhancer`, `DataExtractor`, `LLMJudge`) | Select individually when no module fits, or when the user needs custom control over specific steps |

**Example -- incident reporting from spoken observations:**

- Input: audio recording
- Output: structured incident report JSON
- Selected pipeline (no single module covers the full chain including validation):

  1. `Transcriber` -- speech to text
  2. `TranscriptEnhancer` -- ASR error repair
  3. `SchemaGenerator` -- build typed extraction schema
  4. `DataExtractor` -- fill schema fields from transcript
  5. `LLMJudge` -- hallucination and completeness validation
  6. Human review -- approve before submission

### 4.3 Schema Designer

The Schema Designer agent handles structured output definition for extraction and generation use cases. It takes field definitions collected by `SpecificationBuilder`, invokes the GAIK `SchemaGenerator` component, and produces `output_schema.py` (typed Pydantic model) and `requirements.json` (parsed field specifications). These files are referenced by `BlueprintBuilder` and by the runtime `DataExtractor` or `VisionExtractor`. By making schema design a named agent step, the wizard can explicitly ask the user to review and confirm the output schema before component selection proceeds.

### 4.4 Visual Workflow

The **BPMN visual blueprint** is the business-process view of the solution — a standards-based BPMN 2.0 model for stakeholder communication and governance, derived from the JSON blueprint. See §15 for full details.

### 4.5 Proof of Concept

The proof of concept is a minimal executable implementation that demonstrates the core workflow with uploaded or synthetic data. It should allow users to inspect outputs and adjust prompts, schemas, model parameters, and validation settings.

### 4.6 Final Use-Case Package

The final use-case package is a standard executable project folder containing all files needed to run, test, evaluate, and document the use case.

## 5. Release Plan

### Release V1 -- Current Release

**Target**: Claude Skill deployable in Claude Desktop, Claude Code CLI, or via the Claude Agent SDK (web interface). Conversational, file-based, single `SKILL.md` agent — no sub-agents.

**Capabilities**:
- Full requirement collection dialogue using all fields defined in Section 8 (business-level, technical-level, target output requirements), collected in thematic rounds
- Three §8.1 fields (`use_case_name`, `domain`, `knowledge_processes`) captured in Phase 1; remaining fields collected in Phase 2 thematic rounds
- Requirement **completeness gate** (Section 9 checklist, 13 points) before component selection; the wizard asks follow-up questions for missing items instead of silently recording assumptions
- Pattern classification (audio-to-structured, document-to-structured, RAG, classification, hybrid)
- **Component-option awareness**: the wizard reasons about the behaviour-changing options each component/module class exposes and either infers them from the collected requirements or clarifies them with the user (e.g. Finnish audio → `Transcriber(enhanced_transcript=True)` instead of a separate `TranscriptEnhancer` step; `human_review=yes` → `VisionExtractor(include_verification=True)`)
- **Reference-card completeness**: every component/module in the registry has a reference card with structured `options` (behaviour-/selection-relevant options with `infer_from` hints).
- JSON blueprint generation with ArtifactRegistry enforcement
- BlueprintValidator: artifact existence, component compatibility, required parameters, acyclicity, terminal step, redundancy warnings
- **BPMN 2.0 visual blueprint** (`workflow.bpmn`): a standards-based business-process model with swimlanes for each stakeholder role, typed tasks (user tasks, automated AI steps, human-review tasks, send tasks), parallel and exclusive gateways, data objects, data stores, and message flows. Linked element-by-element to the JSON blueprint via `visualizations.bpmn_mapping`. Changes are made in the JSON blueprint and the BPMN is regenerated — never edited directly.
- Mermaid workflow diagram (`workflow.mmd`): a lightweight flowchart for quick technical validation during development.
- PoC scaffolding: minimal runnable Python package from the blueprint, with schema generation (one SchemaGenerator API call), extraction prompt, evaluation script, and sample-input support
- PoC validation and refinement (Gate 3): the wizard classifies feedback as intent changes (blueprint-first) or implementation fixes (PoC direct)
- **Documentation suite** generated immediately after PoC scaffolding (see Section 18): GenAI product canvas, technical specification, user guide, developer guide, evaluation plan. Documents are pre-filled from blueprint facts; narrative markers are filled by the agent.
- `governance.data_handling` is recorded as descriptive metadata in every blueprint

**Information retrieval model:**

The registry is the index; files are the content. Each agent reads only what it needs:

| Agent | Information source |
|-------|--------------------|
| `ComponentSelector` | Registry JSON fields (`input/output_artifact_types`, `best_for`, `known_limitations`) + reference-card `options` |
| `BlueprintBuilder` | Registry JSON + `example_blueprint_steps` + reference cards |
| `PoCScaffolder` | `readme_path` + `example_script_path` + reference cards |
| `PackageBuilder` | `readme_path` + `example_script_path` + reference cards |

## 6. High-Level Workflow

```
1.  Session start and use-case intake
2.  Collect requirements (full collection in V1; complete in V1+)
3.  Generate structured specifications (business_spec, technical_spec, target_output_spec)
4.  [Gate 1] Validate specifications with the user
5.  Design output schema (conditional -- typed structured-output use cases)
6.  Select GAIK modules and components
7.  Declare artifacts (ArtifactRegistry) and generate the executable JSON blueprint
8.  Generate visual workflow (Mermaid diagram + BPMN)
9.  [Gate 2] Validate workflow with the user
10. Create proof of concept
11. [Gate 3] Run PoC, collect feedback, and refine prompts/schemas/parameters/components
12. Generate the documentation suite
```

Steps 1-12 correspond one-to-one with the detailed phases in Section 7. Gates 1, 2, and 3 are the mandatory hold points — the wizard does not advance until the user confirms at each one.

## 7. Detailed Workflow

| Phase | Description |
|-------|-------------|
| **1. Session start** | Wizard asks for an output directory and a plain-language use-case description, then classifies the pattern (audio-to-structured, document-to-structured, RAG, classification, hybrid, etc.). |
| **2. Requirement collection** | Collects the full Section 8 model in thematic rounds (business, technical, target output). Asks follow-up questions for any missing item rather than assuming. |
| **3. Specification generation** | Produces `business_spec`, `technical_spec`, and `target_output_spec` and presents a concise summary for confirmation. |
| **4. Gate 1 — Specification validation** | User approves or amends the specification. Wizard does not proceed until confirmed. |
| **5. Schema design** *(conditional)* | For typed structured-output use cases: invokes `SchemaGenerator` to produce `output_schema.py` and `requirements.json`. Presented to the user for approval before proceeding. |
| **6. Component selection** | Agent reads the registry (`best_for`, `known_limitations`, artifact types) and applies the module-first rule. Provides a short selection rationale and traceability table. |
| **7. Artifact declaration + blueprint generation** | Declares each transformation step as a typed, named artifact. Creates the executable JSON blueprint. |
| **8. Visual workflow generation** | Generates the BPMN visual blueprint (`workflow.bpmn`) and Mermaid diagram (`workflow.mmd`) from the JSON blueprint. Both are derived views — never hand-edited. |
| **9. Gate 2 — Workflow validation** | User reviews the visual workflow. Changes are made to the JSON and diagrams are regenerated. |
| **10. PoC creation** | Scaffolds a minimal runnable Python package with `run_poc.py`, schema, prompt, config, and eval script. Prints a use-case-specific handoff message with exact run instructions. |
| **11. Gate 3 — PoC validation and refinement** | User runs the PoC and shares the output. Wizard diagnoses issues, proposes blueprint diffs for approval, regenerates affected files, and loops until the user is satisfied. |
| **12. Documentation suite** | Generates the documentation suite into `<output_dir>/docs/` (five documents from blueprint facts: GenAI product canvas, technical specification, user guide, developer guide, evaluation plan). |

| Field | Description |
|-------|-------------|
| `input_types` | Audio, video, PDF, DOCX, image, text, database, API, or mixed |

| Field | Description |
|-------|-------------|

## 9. Requirement Completeness Checklist

Before the wizard generates a blueprint, it verifies that the following questions have been answered or explicitly marked as unknown:

1. What task should the system support?
2. Who will use the system?
3. What input artifacts will the system receive?
4. What output should the system produce?
5. Which fields, sections, or answer types are required?
6. What language is used in the input and output?
7. Is domain-specific vocabulary needed?
8. Does the use case require human review?
9. Are there privacy, security, or compliance constraints?
10. Should the solution use a specific model provider?
11. Should the output be integrated into another system?
12. How should quality be evaluated?
13. What should the first PoC demonstrate?

Unanswered questions are asked as follow-ups rather than silently assumed.

## 10. JSON Blueprint Design

The JSON blueprint is the executable source of truth. It should be generated after specification validation and updated after each major change.

### 10.1 Required Top-Level Sections

```json
{
  "blueprint_version": "1.0",
  "metadata": {},
  "use_case": {},
  "business_spec": {},
  "technical_spec": {},
  "target_output_spec": {},
  "assumptions": [],
  "artifacts": {},
  "inputs": {},
  "outputs": {},
  "schemas": {},
  "components": {},
  "workflow": {},
  "prompts": {},
  "models": {},
  "validation": {},
  "evaluation": {},
  "governance": {
    "data_handling": {}
  },
  "runtime": {},
  "package": {},
  "visualizations": {},
  "traceability": [],
  "change_log": []
}
```

> **Artifact authority**: `artifacts` is the canonical registry of all data objects in the pipeline. `inputs` and `outputs` are optional business-facing summaries for UI grouping and generated documentation (e.g. the GenAI product canvas); they are not authoritative. BlueprintValidator must derive artifact existence, type, and flow from `artifacts`, not from `inputs` or `outputs`. Future implementers should not add artifact definitions to `inputs`/`outputs` that do not also appear in `artifacts`.

> **`target_output_spec`**: holds the structured-output field definitions described in Section 8.3 (field names, types, required flags, allowed values, missing-value policy). It is the input that `SchemaDesigner` (Section 7.5) consumes to generate `output_schema.py` and `requirements.json`. For RAG or other non-extraction use cases it may be empty or omitted.

> **`visualizations`**: holds the file paths of the generated visual workflows (`workflow.mmd` in V1, `workflow.bpmn` in V1+) relative to the output directory. It is populated by `WorkflowVisualizer` as a convenience index; the diagrams themselves are always regenerated from `artifacts` and `workflow`, so this section is not authoritative.


**Reference files:**

| Artifact | Path |
|---|---|
| JSON Schema (Pydantic-generated) | `implementation_layer/solution_wizard/schemas/use_case_blueprint.schema.json` |
| Worked example blueprint | `implementation_layer/solution_wizard/examples/incident_reporting_blueprint.json` |

Regenerate the schema: `python scripts/run_wizard.py --export-schema`

## 11. Component Registry

The wizard uses a component registry for repeatable selection decisions. The registry file is at:

```
implementation_layer/solution_wizard/registries/gaik_component_registry.json
```

Each entry describes a component's `input_artifact_types`, `output_artifact_types`, `best_for`, `known_limitations`, `required_parameters`, `supported_providers`, and file paths (`source_path`, `readme_path`, `example_script_path`). Selection is agent-driven — there are no scoring rules. The agent reads these fields and reasons from them. Adding a new component requires only a new registry entry (plus a reference card).

**Module entries** also include `uses_components` — the internal building blocks the module orchestrates. `ComponentSelector` uses this to show the user what a module contains and to decompose it into explicit steps when the user needs custom control.

**Reference cards** (`registries/component_reference_cards.json`) record the verified call pattern for each component: import line, constructor, primary method, return shape, and behaviour-changing options with `infer_from` hints. Cards are used by `PoCScaffolder` to wire components correctly without guessing API signatures.

**Categories covered:** transcription, transcript enhancement, document parsing, vision parsing, schema generation, data extraction, document classification, RAG, validation, evaluation.

## 12. Component Selection Guidance

Selection is agent-driven (Section 3.4): the agent reads the registry fields and reasons from them. It is **not** a deterministic rule engine. The only deterministic elements are the module-first rule and the `BlueprintValidator` safety net; everything else is the agent's interpretation. The agent also records why a component was *not* selected when there are plausible alternatives.

The table below is **guidance the agent uses, not a lookup it is bound to** -- common requirement patterns and the typical selection. The agent may deviate when the use case calls for it (and the validator will still enforce type compatibility).

| Requirement Pattern | Typical Selection |
|--------------------|----------------------|
| Audio input + structured JSON output | `AudioToStructuredData` |
| Audio input + transcript output only | `Transcriber`, optionally `TranscriptEnhancer` |
| PDF/DOCX input + structured JSON output | `DocumentsToStructuredData` |
| Scanned or visually complex documents | `MultimodalParser`, `VisionPlusParser`, or `VisionExtractor` |
| Images or blueprints to structured output | `VisionExtractor` or vision parser + extractor |
| Document collection + question answering | `RAGWorkflow` |
| Search over video transcripts | `Transcriber` + RAG components |
| Document type detection | `DocumentClassifier` |
| Natural-language database questions | `PostgresAgent` |
| Field-level extraction quality metrics | `ExtractionEvaluator` |
| RAG quality metrics | `RAGEvaluator` |
| Hallucination or faithfulness checking | `LLMJudge` or `LLMJudgePanel` |

## 13. Visual Workflow Generation

### 13.1 Mermaid

Mermaid is generated alongside the BPMN visual blueprint as a lightweight flowchart for quick technical validation during development. It is easy to include in Markdown and renders directly on GitHub. Both diagrams are derived from the executable JSON blueprint and are never hand-edited; the BPMN is the primary view for stakeholder communication and business-process review.

### 13.2 BPMN

The BPMN visual blueprint is the standards-based business-process view of the solution. It is derived from the JSON blueprint and linked to it element-by-element through `visualizations.bpmn_mapping`. It shows:

- Process start and end
- Lanes for users, reviewers, GAIK tool, and external systems
- User tasks and automated tasks
- Decision gateways and data artifacts
- Databases or external systems
- Review and rework loops

The BPMN is regenerated from the JSON blueprint and never edited directly. During PoC validation, the wizard updates the JSON based on user feedback and regenerates the BPMN accordingly — the user does not edit the BPMN file itself. The generated file can be opened in any BPMN 2.0-compatible tool (bpmn-js, Camunda Modeler, draw.io) for review, export, and stakeholder communication.

## 14. Proof-of-Concept Structure

The PoC should be small, runnable, and easy to inspect. It demonstrates the main value of the use case without requiring a full production setup.

```
poc/
    README.md
    run_poc.py
    requirements.txt
    .env.example
    config.yaml
    sample_input/
    output/
    schemas/
        output_schema.py
        output_schema.json
    prompts/
        extraction_requirements.md
        validation_rubric.md
    evals/
        run_basic_eval.py
```

The PoC supports two execution modes:

1. **User-data mode**: the user provides real sample files placed in `sample_input/`.
2. **Synthetic-data mode**: the wizard generates small artificial examples for testing the pipeline and places them in `sample_input/` automatically.

The PoC writes all outputs to the `output/` folder and avoids modifying external systems.

**Generated `README.md`**

The wizard generates a use-case-specific `README.md` -- not a generic template. It contains:

- Prerequisites: Python version and `pip install -r requirements.txt`
- Environment setup: which variables to set in `.env` and where to get the values (e.g. Azure API key, endpoint)
- Input instructions: exact file name, format, and location expected by `run_poc.py` for this use case
- Run command: the exact command to execute
- Expected output: what the result file looks like and where it is written
- Adjustment guide: which file to edit for each type of change -- prompt wording (`prompts/`), output fields (`schemas/`), model or temperature (`config.yaml`)

This means a user who has never seen the wizard before can pick up the generated folder and run the PoC without returning to the wizard conversation.

## 18. Security, Privacy, and Governance

Every blueprint includes a `governance.data_handling` section (see Section 10.6). Default rules:

1. Do not automatically submit generated outputs to external systems without user approval.
2. Include human review for high-impact or safety-related outputs.
3. Store secrets only in environment variables, not in generated code.
4. Include `.env.example`, but never include real keys.
5. Record whether external model APIs are allowed.
6. Record whether local processing is required.
7. Record data-retention assumptions.
8. Log model usage and cost where relevant.
9. Keep prompts, schemas, and model settings versioned.
10. `audit_log_required` defaults to `true` for safety, HR, finance, and legal use cases.
11. `contains_personal_data: "unknown"` and `output_sensitivity: "unknown"` are surfaced to the user as open questions (descriptive metadata; non-blocking).

## 21. Implementation Design

The wizard is implemented as a single consolidated package at `implementation_layer/solution_wizard/`. The SKILL.md (the conversational orchestration layer) and all Python implementation code (validators, scaffolders, generators) live together in one location, versioned and deployed as a unit.

### 21.1 Two-Layer Architecture

The wizard has two layers inside the same package:

| Layer | What it contains | Role |
|-------|-----------------|------|
| **SKILL.md** | Conversation flow, question phrasing, phase sequencing, script invocation calls | Orchestration -- the pilot |
| **Python scripts and modules** | Blueprint validation, registry lookup, Mermaid/BPMN generation, PoC and package scaffolding, change operations | Implementation -- the aircraft |

The SKILL.md calls the Python scripts by relative path. The scripts are independently runnable from the command line, callable from CI, and testable without a Claude session.

The proposal-validation loop is enforced at the code level -- the LLM may draft proposals but no change is persisted until validation passes and, where required, the user approves:

```
LLM proposes -> validate_blueprint.py checks -> User approves -> Blueprint updates
```

## 23. V2 — What's Planned

V2 is aimed at making the wizard production-grade and accessible to a wider audience through a dedicated web UI. All V1 capabilities carry over unchanged. The following new capabilities are planned:

**Dedicated Solution Wizard web UI**
A purpose-built web application that hosts the entire wizard workflow — from requirement collection through blueprint design to PoC validation and package generation — in a structured multi-pane workspace. This replaces the current dependency on Claude Code/Desktop or a raw chat interface. The UI is intended to be self-contained and usable by domain experts without a developer tool installed.

**Interactive BPMN editing**
Within the Solution Wizard UI, the BPMN canvas becomes directly editable. Changes made through the canvas, a step configuration panel, or natural-language chat are converted to structured JSON change operations, validated by `BlueprintValidator`, and reflected back in the JSON blueprint. The BPMN is regenerated from the updated JSON — the JSON remains the source of truth. All changes are logged and reversible.

**Full use-case package generation**
Generates a standard installable Python project (beyond the PoC): `src/`, `configs/`, `schemas/`, `prompts/`, `evals/`, `tests/`, `scripts/`. The package is executable from the command line and production-grade.

**Gate 4: runtime validation of the full package**
Runs the generated test suite (`tests/`) and evaluation scripts (`evals/`) against the full package inside the wizard UI before the package is declared production-ready. Gate 3 covers the PoC only; Gate 4 validates the full deliverable.

**Error handling and guardrails**
Robust error handling and configurable guardrails for safe, production-grade use of the wizard:

- **Error handling** — standard production-grade error handling across all wizard operations: meaningful error messages with actionable guidance, retry logic for transient API failures, input validation at system boundaries (file formats, blueprint structure, registry constraints), and structured logging for diagnostics and audit.
- **Wizard guardrails** — scoping and safety constraints to keep the wizard within its intended boundaries: generation is limited to use cases supported by the GAIK toolkit (the wizard declines out-of-scope requests); constraints on what can be generated or modified (e.g. approved schemas are protected from overwrite); human review is enforced for safety-critical, legal, or high-impact outputs; cost and token usage are bounded to prevent runaway sessions; and generated packages cannot write to paths outside the user-specified output directory.
- **Graceful error recovery** — clear error messages mapped to actionable guidance; failed steps (API calls, script runs, file writes) surface the root cause and suggest a fix rather than silently failing.
- **Session and state safety** — auto-save of blueprint state so an interrupted session can be resumed without data loss; protection against partial writes that could leave the blueprint in an inconsistent state.

**Staged sub-agents (optional)**
If package generation and interactive BPMN editing grow the conversation state beyond a single context window, individual pipeline stages may be split into independent agents each receiving `use_case.blueprint.json` and returning a validated diff. The pipeline shape (§3.8) is unchanged; this is a realization choice, not a design change.
