**AI Maturity Level**
Frame Rate is a startup specializing in immersive experiences, film production, brand partnerships, and AI visuals. The company is developing an interactive physical installation that uses motion sensors and a modular frame structure to create sound and light experiences in physical spaces. The solution has been piloted using ultrasonic sensors and pre-composed sound palettes, where visitors move through a tunnel-like structure and receive a unique audio file via QR code. Current sound and lighting control is based on statistical and hand-coded methods in Max/MSP, with no machine learning in the current system. The company has used or considered AI for generating music and has experimented with detecting emotional states from facial expressions, but there is no current production AI system for the installation. The core physical concept is at the prototype and pilot stage, while the AI-related part is still in ideation and early conceptual design. Based on the existing prototype, some AI experimentation, limited AI workflow integration, and the absence of a production AI pipeline, Frame Rate’s AI maturity level is **low.

**Current Solution Development Stage**
Frame Rate is in the prototype and pilot stage for the physical installation, and in the ideation and early conceptual design stage for the AI components. The current system uses Max/MSP as the software hub, receiving serial data from ultrasonic sensors and mapping movement to sound and lighting through hand-coded statistical methods. The company has identified limitations with the current ultrasonic sensors, especially around latency and accuracy, and is moving toward depth cameras and motion sensors. For AI implementation, the company wants visitors to speak or type a desired music style before entering the installation. The system would then select matching audio from a database of generated or pre-produced sound material, and movement data would affect the playback and processing of the selected audio. Frame Rate is currently looking for practical technical guidance on speech input, audio metadata, audio matching, dataset creation, and what level of real-time audio response is feasible with current AI capabilities.

**Recommendations**
•	Focus the first AI implementation on speech or text-based audio selection rather than real-time generative audio. The current idea of generating music on demand is likely too slow and unpredictable for the installation experience, while selecting from a prepared audio database is more practical and technically feasible.
•	The recommended near-term pipeline is to convert the visitor’s voice input into text, match that text against metadata for available audio files, retrieve the closest matches, and select the best option for playback in Max/MSP or another audio playback system. This keeps the AI role clear and avoids adding unnecessary latency to the movement-based part of the installation.
•	Create a small proof-of-concept dataset before attempting a large audio library. A practical starting point would be metadata for a limited set of audio files, enough to test whether user prompts such as “saxophone jazz” or “80s music with 120 BPM” return suitable results. Once the matching behaviour is understood, the dataset can be expanded.
•	The quality and structure of audio metadata should be treated as a key success factor. Each audio file should have useful text descriptions and relevant attributes, such as genre, mood, instrumentation, tempo, energy, and other audio characteristics that matter for the installation. Good metadata will make it easier for the matching system or agent to return audio that feels close to the visitor’s request.
•	Metadata extraction can be handled as an offline process. Metadata does not need to be extracted every time the installation runs. Existing audio files can be processed once, and new files can be processed when they are added. This makes the workflow more manageable and avoids unnecessary real-time computation.
•	Consider testing OpenAI’s voice agents or agent SDK approach. A voice agent could handle speech input, interpret the request, decide which metadata fields to use, and search or filter the database. This may reduce the amount of manual pipeline work, provided the audio database and metadata are structured clearly.
•	The company can also investigate APIs for music generation tools such as Suno or Udio-style services to help build the audio library. This should be treated as a separate offline dataset creation task, not as a real-time generation step during the visitor experience.
•	The existing movement-to-sound and movement-to-light mapping should remain statistical and hand-coded for now. The current Max/MSP-based approach already works and is likely to be more responsive than a generative AI model. Replacing this layer with AI may increase latency and reduce the immediacy that is important for an interactive installation.
•	AI-based movement-to-sound processing can remain a research direction, but it should not be the first implementation priority. If Frame Rate later wants to test this, it would likely require a lightweight model that can process sensor data with very low latency. Converting movement data into text and sending it to an LLM is technically possible, but it would extend the pipeline and is unlikely to be responsive enough for real-time interaction.
•	Proceed by building the first version internally, using a small audio dataset, speech-to-text, metadata matching, and optional embeddings or a voice agent. After that, a follow-up advisory meeting would be useful to review the implementation, identify issues, and decide whether further support is needed.
•	At this stage, the use case does not appear to require a separate FAIR proof-of-concept development service. The more suitable path for the company is to develop the initial implementation on their side, then use further AI advisory meetings for review, technical feedback, and next-step planning.
•	A follow-up meeting before mid-June would be useful if Frame Rate has enough time to test the initial workflow. If not, the next review can be scheduled after the summer, with the focus on what was implemented, how the matching performed, and whether the next step should be dataset expansion, agent-based search, or more advanced movement-to-audio experimentation.
