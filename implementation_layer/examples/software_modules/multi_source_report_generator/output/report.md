# AI Consultancy Report

## AI Maturity Level
The company is developing an interactive system that combines sensor input, sound, and lighting through Max/MSP, with serial data from low-cost ultrasonic sensors feeding a software hub that maps movement to audio and lighting changes (framerate.mp3). The current system uses statistical and manual methods rather than machine learning, and the main AI interest is in adding speech-to-text and text-to-audio matching against a future music database rather than replacing the existing movement pipeline (framerate.mp3). The discussion focused on technical options, limits around latency, and how the company could progress toward an AI-enabled proof of concept for music selection and interaction. Based on the evidence, the company’s AI maturity is **Low** because there is currently no machine learning in production, the music metadata dataset still needs to be created, and the AI roadmap is still at the level of exploratory design and advisory support rather than implementation (framerate.mp3).

## Current Solution Development Stage
- **Current phase is early ideation with an existing non-AI system:** The company already has a functioning interactive system that maps sensor-based movement to sound and lighting using statistical and manual methods, but the AI component has not yet been built and is still being discussed conceptually (framerate.mp3).
- **No machine learning is currently in use:** The speaker explicitly stated that “there's actually no machine learning” in the present system and confirmed that it is not a generative AI model, which places AI development before prototyping in practical terms (framerate.mp3).
- **A clear first AI use case has been identified:** The main near-term AI objective is to take speech or text input describing desired music, convert it to text if needed, and match it against audio metadata in a database so the most relevant pre-generated music can be selected (framerate.mp3).
- **The movement-to-sound pipeline is already functional without AI:** The current body or movement mapping works through statistical analysis such as acceleration, velocity, and location, and this is considered effective and responsive enough for real-time use at present (framerate.mp3).
- **Low-latency constraints shape AI readiness:** The team is cautious about using generative AI for movement-to-sound control because latency above roughly 100 milliseconds was described as harmful to the user experience, and advisors noted that such models would likely increase delay and hardware demands (framerate.mp3).
- **Data readiness is incomplete:** The company does not yet have the target audio database or metadata set in place, and the speaker said they still need to determine the size, diversity, and generation process for the musical material that would support matching (framerate.mp3).
- **Technical direction for a prototype was suggested:** Advisors proposed starting with speech-to-text using OpenAI speech models, generating or extracting metadata for a limited set of audio files, and then testing either direct LLM matching for small collections or embedding-based retrieval with cosine similarity for larger sets (framerate.mp3).
- **What exists versus what still needs development is clearly separated:** The real-time interactive artwork infrastructure exists, but the AI-related pieces that still need development include speech recognition integration, metadata generation or extraction, audio database construction, retrieval logic, and user testing of match quality (framerate.mp3).
- **The company is looking for practical implementation guidance rather than outsourced build work:** The speaker asked for suggestions on speech recognition, embeddings, and next technical steps, while the advisors clarified that this use case is considered simple enough for the company to build itself with advisory follow-up rather than a formal proof-of-concept service (framerate.mp3).
- **The immediate aim is proof through user response:** The stated ultimate goal is to test the system with people and see whether the returned music feels close enough to the request, which shows the next milestone is experiential validation rather than commercial deployment (framerate.mp3).

## Recommendations
1. **Start with the speech-to-text plus text-to-audio matching path** — This was presented as the most reasonable and simpler AI direction because the current movement mapping already works, while real-time generative movement-to-sound modeling would likely add latency and complexity without clear benefit (framerate.mp3).
2. **Keep the existing statistical movement-to-sound system in place for now** — The current pipeline is functioning and responsive, and the discussion repeatedly noted that replacing it with AI could make the experience feel delayed or “gummy,” which would undermine the installation’s real-time quality (framerate.mp3).
3. **Build a small proof-of-concept dataset before scaling up** — The advisors suggested beginning with a limited number of audio files and metadata entries to test how the voice agent or retrieval workflow performs, rather than waiting until a very large library has been created (framerate.mp3).
4. **Create or collect structured metadata for each audio item** — Match quality depends on metadata quality, and the meeting emphasized that the usefulness of the retrieval system will largely depend on how well the music is described in text form (framerate.mp3).
5. **Use speech recognition only where it adds practical value** — The conversation noted that the input can be speech or direct text, so the implementation can stay flexible and avoid unnecessary complexity when typed text is available (framerate.mp3).
6. **Use OpenAI speech models for English-language transcription as a starting point** — GPT-4o transcribe was recommended as performing very well for English, with Whisper noted as an open source alternative if local deployment later becomes relevant (framerate.mp3).
7. **Choose the retrieval method based on dataset size** — For a few hundred audio items, the advisors said embeddings may not even be necessary because an LLM may be able to rank directly; for several thousand items, embeddings with similarity search were recommended as the better structure (framerate.mp3).
8. **If the library grows, store embeddings in a database and use cosine similarity matching** — The suggested technical path was to generate embeddings with a text embedding model, store them for reuse, and compare new user requests against them with standard similarity functions (framerate.mp3).
9. **Consider a retriever-plus-ranking pattern for better selection quality** — One proposed architecture was to convert the query into embeddings, retrieve the top candidates, and then let an LLM rank the best match, which fits the company’s need for descriptive matching rather than generation (framerate.mp3).
10. **Treat metadata extraction as a one-time or occasional processing task** — Advisors noted that when new audio is added, metadata generation can be run in batch rather than in real time, which keeps the live experience lighter and more manageable (framerate.mp3).
11. **Explore automated metadata generation for audio if manual labeling is too slow** — The meeting included the view that models likely exist to describe audio or generate metadata, and this could reduce the burden of preparing a usable music library (framerate.mp3).
12. **Parallelize dataset creation where possible** — The company expressed interest in generating musical material through tools such as Juno or Udio and then processing it into metadata, and this was discussed as a practical way to avoid building the library entirely by hand (framerate.mp3).
13. **Do not prioritize real-time AI generation of full music streams at this stage** — The speaker acknowledged that creating music on the fly from a spoken request within milliseconds or seconds remains difficult, so selecting from pre-generated material is the more realistic route for the current stage (framerate.mp3).
14. **Preserve stem-level control as a future design consideration** — The idea of isolating drums, bass, guitar, saxophone, and other elements so movement can affect them independently is a strong creative direction, but the evidence does not show that this has been implemented yet and it should be treated as a later enhancement (framerate.mp3).
15. **Use the current project goals to define a narrow first success metric** — The clearest objective described in the meeting was whether users feel the returned music matches what they asked for, so the first evaluation should focus on perceived relevance rather than broader AI sophistication (framerate.mp3).
16. **Approach movement-to-sound AI as a research curiosity rather than a core delivery item** — The speaker described this as an area of curiosity, and the advisors were skeptical about current model availability, latency, and hardware feasibility, so it appears better suited to later experimentation than immediate implementation (framerate.mp3).
17. **Build internally and use advisory support as the main external service for now** — The advisors explicitly said this use case does not currently require a separate proof-of-concept service and that the company should proceed with development on its own, returning for further brainstorming and review (framerate.mp3).
18. **Plan the next iteration around demonstrable progress** — The agreed direction was for the company to try the proposed approach independently and come back with results for another advisory discussion, which makes short-cycle experimentation the most suitable next step (framerate.mp3).
