# AI Consultancy Report

## AI Maturity Level

The company is developing an interactive movement-based sound and lighting system. Its current setup uses MaxMSP as the software hub, with serial data from ultrasonic sensors feeding into the system. Sensor inputs are mapped to sound and lighting so that participant movement affects audio parameters, including properties such as musical brightness or filtering and spatialization across a speaker array. The team has also discussed a possible workflow where a participant could describe desired music by speaking or typing.

The current system is functional, but its AI maturity remains at an early and exploratory stage. The current implementation uses statistical methods and manual mappings to convert sensor-based movement into sound and lighting, and AI is not integrated into the live workflow. While there is relevant technical experience in MaxMSP and some experience with audio-to-audio language models, the team is still seeking guidance on core AI implementation topics such as speech recognition, embeddings, and how to begin building a retrieval pipeline. Data needed for the proposed AI workflow, including an established audio library and reliable metadata, is not yet in place, and the AI roadmap is currently focused on proof-of-concept ideas such as speech or text-to-audio matching with a small metadata set. Based on the current development stage, lack of machine learning in the working system, limited AI workflow integration, missing data assets, and an early-stage roadmap, the company’s AI maturity level is rated as low**.

## Current Solution Development Stage

The company is in the ideation and early proof-of-concept stages for AI. They already have a functioning interactive system, but it is not an AI or machine learning product at present. The current setup is built around MaxMSP and uses serial data from inexpensive ultrasonic sensors to map movement to sound and lighting. The client stated that the existing system relies on statistical or manual methods, and explicitly confirmed that there is currently no machine learning and no generative AI model in use.

The immediate AI direction is a text- or speech-to-audio matching workflow rather than changing the existing movement-control system. The client wants participants to be able to speak or type the kind of music they want, have that request interpreted and matched to suitable audio from a database or stems, and then have it loaded into Max or similar software for further movement-based manipulation. They were clear that the main AI question is how to go from user text or speech to finding appropriate audio files, while the movement-based interaction remains separate and is already handled effectively by the current non-AI approach.

In terms of readiness, the company already has several useful foundations in place: a working movement-to-sound and lighting pipeline, an established software environment, and a clear target use case for AI implementation. The current system already analyses movement features such as acceleration, velocity, and location, and maps them to audio properties including brightness, filtering, and spatialization. At the same time, several core elements still need development before an AI proof of concept can be implemented, including a music database or dataset, metadata or descriptions for the audio files, and the speech-to-text and text-matching pipeline. The client also noted uncertainty around the size and diversity of the audio data they would need, and said they have not yet generated the music dataset they are considering.

Their current objective is to identify the next practical steps for building this matching system. They specifically asked about approaches for speech recognition, text embeddings, and how to move from example user requests to metadata across many files. A near-term goal is to start with a small set of audio metadata items to test a proof of concept and assess how a voice-based agent performs. The broader aim is to test the system with people and evaluate whether the retrieved music matches participant requests closely enough. Beyond this, they also expressed exploratory interest in a harder real-time model that links human movement directly to sound processing, but described this as a longer-term possibility rather than the primary implementation focus.

## Recommendations

•	The main recommendation is to focus AI work on the offline preference-input stage, where a participant speaks or types the kind of music they want, rather than on the real-time movement-to-sound stage. In the discussion, this text or speech-to-audio matching problem was consistently treated as the clearest and most feasible AI use case. The movement pipeline is currently handled with statistical methods and was described as already working, while the experts questioned the value of replacing it with generative AI given likely latency and responsiveness trade-offs.

•	A practical near-term path is to frame the problem as speech-to-text plus text-to-text matching. The recommendation was to use GPT-4o Transcribe for English speech recognition, or direct text input where appropriate, and then compare the resulting text with music metadata. This was described as simpler than trying to build a more experimental transmodal system. If current metadata is missing or too thin, the discussion suggested generating richer textual metadata from the audio first and then performing the matching step against that improved description layer.

•	The matching workflow should start with existing embedding and LLM methods rather than custom model development. The experts suggested embedding the audio metadata in advance, converting the user query into embeddings, retrieving the top candidates, and then using an LLM to rank the best result. At the same time, they also noted that if the library is only a few hundred audio items, embeddings may not be necessary at first because a single LLM call may be enough. If the collection grows into the thousands, then storing embeddings and using similarity search such as cosine similarity in a database like Postgres becomes the more suitable path.

•	The strongest technical and business recommendation is to take care with metadata and database design, because retrieval quality depends heavily on how the music is described. The discussion repeatedly returned to the need for metadata that captures the relevant characteristics of each audio asset, whether that is tone, overall description, or more specific features. The framework and API layer were presented as relatively low effort, but the more central task was described as building the dataset and defining the metadata in a specific, useful format. In practice, this means the project’s success is likely to depend less on the choice of agent framework and more on the quality and consistency of the underlying audio descriptions.

•	If metadata is not already available at the required quality, it should be generated as a one-time or occasional pipeline step rather than treated as a continuous burden. The experts said models should be able to produce textual metadata from audio, and they framed this as operationally manageable because the current library could be processed once and then updated only when new audio is added. They also noted that processing the current set could take about a day depending on whether it runs locally or through an API. This makes metadata generation a realistic preparation step for both an existing catalog and a growing music library.

•	The next practical step should be a small proof of concept rather than a full-scale build. The recommendation in the meeting was to begin with a limited set of audio metadata records, test how the voice agent behaves, and then expand the metadata and library only if the early results are promising. An agent-based implementation was specifically suggested, using an OpenAI voice agent or agent SDK so that the system can decide how to search based on the request, for example by combining direct metadata filters with embeddings when the user asks for something more specific such as a style plus BPM range. The experts also indicated that these OpenAI APIs and frameworks offer a relatively low-effort route for early experimentation.

•	Exploratory ideas around AI-driven movement-to-sound mapping, sensor-data reinterpretation through text, and large-scale generated music libraries should remain secondary for now. The client’s curiosity about a real-time transmodal model was acknowledged, but the experts were not confident that a suitable model exists for this use case and noted that extra interpretation stages would likely increase latency. For generated music libraries, unresolved questions remain around dataset size and diversity, even though metadata generation itself was viewed as parallelizable and manageable. The most reliable way to judge progress is therefore user testing: the client should test whether people feel the returned tracks match what they asked for, including concrete expectations such as BPM, and then return with experimental findings for further expert guidance.
