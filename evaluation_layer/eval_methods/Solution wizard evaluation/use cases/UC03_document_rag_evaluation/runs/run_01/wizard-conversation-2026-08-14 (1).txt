**Transformation chain**

```
document_collection + access_manifest  →  role-scoped vector index  →  role-filtered retrieved chunks  →  RAGAnswerRecord (answer + citations + access_decision)
```

**Selected**

```
Module: RAGWorkflow   (contains, internally: Embedder + vector store + Retriever + AnswerGenerator)
  Instantiated twice, once per access level, to satisfy "filter before retrieval":
    - "employee" index  — built only from documents where allowed_roles includes "employee"
                           (employee_travel_policy.pdf, mx200_maintenance_manual.pdf)
    - "manager" index   — built from all three documents (manager is authorized for everything)
  Each incoming query is routed to the index matching its role BEFORE any similarity
  search runs — so a restricted document's chunks are never even present in the search
  space an employee query can reach, not just filtered out afterward.
```

| Option | Value | Why | Effect |
|---|---|---|---|
| `persist` | `True` (local Chroma store) | matches "may use a local vector store" | store survives the run under `poc/chroma_store/` |
| `collection_name` | `gaik_rag_employee` / `gaik_rag_manager` | the mechanism that enforces pre-retrieval RBAC filtering | two physically separate search spaces, one per access level |

| `stream` | `False` (default True) | CLI writes one JSON record per query, not a token stream | full answer string returned synchronously |

**Custom logic layered around the module (not a registry component):** to distinguish a genuine **denial** (Q03 — an employee asking about the manager-only document) from an **honest "not found"** (a permitted-topic question the corpus simply doesn't cover), the PoC also runs an internal-only relevance check against the full ("manager") index — used *solely* to decide `access_decision`/`refusal_reason`, never to source the answer text or citations shown to an unauthorized role. This keeps "denied answers reveal no restricted facts" true by construction.

**Note on customization:** the stock RAG template doesn't cover role-based access control or your exact CLI/output contract, so `poc/run_poc.py` was hand-wired (not left as scaffolder boilerplate). It:
- Drives `RAGWorkflow`'s own parser/embedder/vector-store/retriever directly so every chunk can be tagged with `role_<role>` metadata from `access_manifest.json`, and applies that as a pre-retrieval filter (`Retriever.search(filters=...)`) — unauthorized chunks never enter the model context.
- Runs an internal-only unfiltered check (never exposed as content) to tell a genuine access **denial** apart from an honest **not-found**.
- Calls the LLM client directly for answer generation, since `AnswerGenerator.generate()` hardcodes `temperature=0.0` and would have silently ignored your requested `temperature=1.0` / `reasoning_effort=medium`.
- Builds citations from the actual retrieved chunks (never parsed from the model's text), so a citation can't be fabricated.

To run it:
1. Install dependencies: `pip install -r poc/requirements.txt`
2. Set up your environment: `cp poc/.env.example poc/.env` — fill in your Azure OpenAI key/endpoint

4. Run it: `python poc/run_poc.py --input poc/sample_input/poc_input_bundle.json`
