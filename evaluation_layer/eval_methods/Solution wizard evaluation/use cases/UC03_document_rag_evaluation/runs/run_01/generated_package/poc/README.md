# Manufacturing Knowledge Assistant -- Proof of Concept

Generated by GAIK Solution Configuration Wizard V2.

---

## What this PoC does

Role-aware assistant that answers employee questions from internal policies, equipment manuals, and management documents with citations, enforcing role-based access control so restricted documents are never retrieved or disclosed to unauthorized employees.

---

## Prerequisites

- Python 3.11+
- GAIK toolkit: `pip install -r requirements.txt`
- API credentials (see `.env.example`)

## Running the PoC

```bash
python run_poc.py --input sample_input/poc_input_bundle.json
```

`--input` points at a bundle file; `documents_directory`, `access_manifest`, and
`query_set` inside it are resolved **relative to the bundle file itself**, not
the current working directory. A sample bundle (3 PDFs, an access manifest, and
4 role-tagged queries) is already included under `sample_input/`.

Results are written to `output/answer_records.json`.

---

## How role-based access control works here

`RAGWorkflow`'s convenience methods (`index_documents()` / `ask()`) don't expose
a hook to attach custom metadata or to filter *before* the similarity search, so
this PoC drives the same underlying pieces RAGWorkflow uses internally
(`VisionRagParser`, `Embedder`, `VectorStore`, `Retriever`) directly:

1. **Ingestion** -- every chunk of every PDF is tagged with a `role_<role>`
   boolean flag per role (`employee`, `manager`), derived from
   `access_manifest.json`'s `allowed_roles` for that document.
2. **Retrieval** -- each query is answered using `Retriever.search(question,
   filters={"role_<requesting_role>": True})`. Chroma applies that filter as
   part of the similarity search itself (a `where` clause), so a chunk from a
   document the role cannot access is never a retrieval candidate, let alone
   part of the model's context.
3. **Access-decision classification** -- a second, *internal-only* unfiltered
   search checks whether the best match for the query lives in a document the
   role can't access. If so (and the role's own authorized search found
   nothing better), the query is classified `denied` -- without ever exposing
   that document's content. Otherwise, if even the authorized search found
   nothing relevant, the answer says so honestly (`access_decision: allowed`,
   empty citations, a `refusal_reason` explaining nothing was found).
4. **Citations** are built from the *actual* retrieved-and-used chunk metadata,
   not parsed from the model's free-text answer -- so a citation can never be
   fabricated by the model.

See `classify_and_answer()` in `run_poc.py` for the implementation.

## Expected output

`output/answer_records.json` -- a JSON array with one `RAGAnswerRecord` per
query (see `schemas/output_schema.py`): `query_id`, `role`, `question`,
`access_decision` (`allowed`/`denied`), `answer`, `citations`
(`[file_name, page_number]` pairs), `refusal_reason`.

## Adjusting the PoC

| What to change | Which file |
|----------------|-----------|
| Output schema / fields | `schemas/output_schema.py` |
| Answer-generation prompt / grounding rules | `ANSWER_PROMPT` in `run_poc.py` |
| Model, temperature, reasoning effort | `config.yaml` |
| "Not found" similarity threshold | `NOT_FOUND_FLOOR` in `run_poc.py` |
| Evaluation criteria | `evals/run_basic_eval.py` / `evals/ground_truth/expected_results.json` |
